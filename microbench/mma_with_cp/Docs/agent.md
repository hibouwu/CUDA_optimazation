# tcgen05 micro-benchmark 文档维护摘要

## 写作原则

- 本文档是技术分享文档，因此不能出现实际的仓库路径和在正文中对仓库内容的引用，而是改为对其的描述。
- 正文写实验定义、数据口径和结论，过程记录统一放 agent.md，正文只保留最终口径、实验定义和结论，而是每次直接维护最终版的文档。
- 内部可以做对抗式审查，但正文标题尽量写成读者友好的技术标题，例如“真实性分层”；不要把审查过程写进正文。
- 如果需要说明 SS/TS 真实性分层，放在“真实性分层”或 case 定义中展开。
- 如果需要记录为什么调整口径，放在本 `agent.md`、commit message 或 changelog，而不是放在最终报告背景段。
- 这个文档默认面向初学者，所以要保留初学者解释，不能出现未经定义的术语。
- 结论、正文语气不要有ai味，具体如下：
  - 每段第一句尽量写正向结论，不要先写“不是……”。
  - “不是 A，而是 B”最多偶尔用；频繁出现就改成“本文关注 B，A 暂不讨论”。
  - 用实验动作替代泛泛目的，例如用“测试、比较、记录、核对”替代“拆解、探索、呈现、进行实验”。
  - 句子优先写成“在某架构下测试某对象，比较某指标”，例如“本文在 Thor/SM110 架构下测试 `tcgen05.mma` 的 SS/TS 模式，比较不同 A 操作数来源的性能、完成同步开销，以及 `tcgen05.cp` 的 A tile 准备成本。”
  - 避免名词堆叠。把“操作数来源、完成同步边界、准备成本”这类抽象并列改成“不同 A 操作数来源的性能、完成同步开销、A tile 准备成本”。
  - 用具体对象替代“该方法/该机制/该问题”。
  - 少写“显著、充分、有效、明显、值得注意的是”。
  - 每个结论后面最好接一个证据：shape、K、cycles、TFLOPS、counter 或具体实现现象；正文不写仓库路径。
  - 保留边界，但边界要短，不要每句话都自我否定。
  - 对数据能支持的现象直接写正向描述；否定式边界能删就删，必要边界放在更具体的正向表述后面。
  - 避免直接使用读者不熟的英文瓶颈术语；改成中文现象描述，例如“noise=1 到 noise=2 之间下降最明显”“形成反压，发射端被下游拥塞拖住”。
  - 解释饱和时写清楚是哪条路径进入饱和区。TMEM 写入干扰这里按“写入带宽、端口/pipe、后端排队/仲裁和 completion wait 共同暴露”解释，不把数据直接写成硬件内部严格串行。
