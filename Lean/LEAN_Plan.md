# Lean 形式化建模计划

状态：架构草案。当前只保留本计划；尚未确定 Lean 类型、源码模块、工具链和实现方案。此前原型及其证明数量不作为本计划的完成依据。

## 1. 需求与完成标准

目标是严格推导两类结论：

1. 给定程序与执行规则，所有可达执行都满足哪些依赖、资源和存储生存期性质。
2. 给定必需工作、依赖关系及资源能力上限，所有完成执行的时间至少是多少。

两类结论必须描述同一执行对象，能组合成关于具体流水线的结论。研究收益按“明确了哪些必要前提、排除了哪些非法执行、得到了什么可用界限”评价，不按定理数、文件数或编译通过次数评价。

Lean 负责检查从定义和前提到结论的推导。程序抽象是否符合源码、硬件假设是否符合设备，分别需要程序对应关系与实验依据。形式化不会自动补足这些依据。

首轮完成标准：对一条有限槽流水线，在同一语义中证明可达执行的安全性和完成时间下界，给出可满足的执行实例，并说明改变槽数或一个局部假设时哪些结论受影响。它是组合能力的首轮验证，不是完整 GEMM 验收。

## 2. 从结论倒推数学对象

设 P 为程序描述，H 为明确列出的环境与服务假设，s₀ 为初始状态。执行语义产生可达轨迹集合：

\[
\mathcal R(P,H,s_0).
\]

需要分别建立：

\[
\forall \tau\in\mathcal R(P,H,s_0),\quad \mathrm{Safe}(\tau),
\]

\[
\forall \tau\in\mathcal R(P,H,s_0),\quad
\mathrm{Finished}(\tau)\Rightarrow T(\tau)\ge L(P,H,s_0).
\]

安全性由初态和局部转移规则推出，不能直接塞进可达轨迹的定义。下界对所有符合前提的完成执行成立，不能仅对某个模拟器生成的排程成立。两者都不自动证明无死锁或最终完成；若研究最终完成，需另列进展、公平性及服务完成假设。

由此需要以下职责，而不是先规定文件数量：

| 对象 | 必须表达的内容 | 不承担的职责 |
|---|---|---|
| 程序 P | 操作身份、参与者、必需依赖、工作量、存储对象及代次 | 不隐含未知硬件延迟或服务顺序 |
| 假设 H | 资源作用范围、容量、服务约束、仲裁条件及时间口径 | 不把经验拟合当作硬件事实 |
| 状态与执行语义 | 局部动作的允许条件、状态更新、事件生成 | 不预先要求待证明的全局安全结论 |
| 执行轨迹 τ | 同一次执行的事件、状态变化与时间 | 不另存一份可独立修改的资源账本 |
| 派生量与性质 | 占用、工作守恒、依赖路径、计时终点与下界 | 不重新定义另一套执行过程 |

这里的“同一语义”不要求所有对象塞进一个结构。独立抽象可以保留，但必须有从共同执行对象到该抽象的明确映射及适用条件；需要组合的性质必须能沿映射回到同一轨迹。

## 3. 定义归属与依赖方向

建议的逻辑依赖为：

```text
程序描述 + 环境假设 + 初始状态
                  ↓
             执行语义
                  ↓
        可达轨迹及其派生量
           ↙             ↘
     安全与守恒性质      时间下界
           ↘             ↙
          同一实例的组合结论
```

实验记录不参与定义通用定理。只有实例化某个硬件假设时，才引用其证据与适用范围；更换证据或参数不应迫使无关的结构性证明重做。

| 内容 | 定义归属与维护方式 |
|---|---|
| 现有术语和问题范围 | 参考现有接口与程序图文档；遇到歧义先明确语义，不直接机械翻译 |
| 形式化语义 | 实现阶段由 Lean 定义承担权威来源；文档解释定义，不并列维护另一套规则 |
| 具体程序输入 | 绑定一个明确的程序实例；如需导入，则固定导出格式并校验结构条件 |
| Python 模拟器 | 继续承担现有数值预测；首轮不在 Lean 重写第二套完整模拟器 |
| 硬件参数和实验身份 | 仍由原记录维护；Lean 中以显式前提或实例参数引用 |

共享 schema 只能减少表示差异，不能证明语义等价。后续如要对 Python 输出作保证，应选择明确的连接方式：检查一条输出轨迹满足形式规范，或证明某个生成算法符合规范。前者只覆盖该轨迹；后者覆盖算法的声明输入域。当前不同时建设两条路线。

## 4. 第一份组合证明的候选

建议从“有限槽的搬运—消费流水线”开始，直接检验槽约束能否参与时间推导。先限制为有限工作项、单生产者和单消费者；具体事件含义按现有程序图选取，避免把抽象生命周期默认等同于 PTX barrier 语义。

输入需要明确：工作项数量 n、槽数 S、每项的身份与代次、取得/数据可用/消费完成/释放事件、必需工作量、服务约束、初始占用及计时区间。n、S 与服务参数尽量保留为符号。

拟建立的结论依次为：

1. 从局部动作规则推出：旧代必要读取完成前不能被新代覆盖；资源取得与释放守恒；占用不超容量。
2. 从同一轨迹提取必需依赖路径、资源工作量和槽占用区间。
3. 分别推导路径、服务能力和有限槽约束产生的时间下界，再在同一计时边界下组合。
4. 构造完整执行，检查前提可满足；给出一个槽数改变后，下界或可行排程确实改变的实例。

例如，若全部 n 项工作都在 [0,T] 内取得并释放槽，每项的必要占用时长下界为 ℓᵢ，且任意时刻最多占用 S 个槽，则应能从占用区间推出：

\[
\sum_i\ell_i\le ST.
\]

这条结论只有在占用与释放来自同一执行语义、ℓᵢ 的下界有依据时才有用途。不能把它直接当作新公理，也不能忽略计时开始前已有占用或结束后的未释放工作。

对于资源 r，若 Dᵣ 是计时区间内不可省略的需求，μᵣ 是同单位的有效服务率上限，则还需由服务语义推出 Dᵣ ≤ μᵣT。不同资源允许重叠，不直接相加各自时间。实测有效带宽不自动提供 μᵣ 所要求的上限。

这些是拟证明的陈述，尚未确定其 Lean 表达或证明方法。若首轮只能得到互不关联的槽安全和算术不等式，说明组合目标没有完成，应调整定义而不是增加更多孤立定理。

## 5. 实现前需要解决的设计选择

| 选择 | 决策依据 |
|---|---|
| 时间域 | 确认首个实例需要整数 tick、有理数还是实数；固定计时起终点。不得因实现方便默认 cycle 与 ns 可互换 |
| 事件粒度 | 保留首个结论需要的完成、可见、消费及释放区别；不强制所有操作具有相同的事件总顺序 |
| 状态粒度 | 保留对象身份、完整代次和实际共享范围；明确哪些历史可以安全省略 |
| 服务表达 | 先判断结论只需能力上限，还是需要具体仲裁/排程；推导下界时尽量使用较弱前提 |
| 与既有程序的关系 | 选定一个程序图片段，写明抽象覆盖和省略内容；未建立对应前，不把结论归于该实现 |

不能仅因某条规则容易证明就采用它。尤其是硬件下界：若抽象排除了硬件允许的更快执行，则抽象中的下界未必适用于硬件。必须论证相关执行被覆盖，且时间和必需工作量的对应方向正确。

## 6. 推进次序与维护边界

| 步骤 | 产物 | 完成依据 |
|---|---|---|
| 先写定理陈述 | 第一份组合结论的输入、量词、前提、输出和一个具体实例 | 能解释该结论解决什么问题；前提中没有藏入结论 |
| 再定语义 | 最小对象、局部规则、派生量和定义归属 | 所有目标能在同一执行上陈述；未决选择已解决 |
| 再实现证明 | 支撑该组合结论所必需的定义与引理 | 定理陈述经人工核对，Lean 检查通过，前提可满足 |
| 最后检验复用 | 改变槽数或一个局部条件的第二实例 | 沿用同一语义和通用证明，明确变化影响范围 |

前三步完成前不启动 Python 映射工程或 GPU 补测。某一步需要不断引入与首个结论无关的对象时，先缩小目标或调整边界，不自动扩张为通用 GPU 形式化框架。

维护约束：

- 每个定义只有一个维护位置；不为每轮讨论复制状态机、规则集或入口。
- 每个模块能说明自己的输入、结论和依赖；读定义与依赖即可恢复上下文，不靠重跑历史实验猜测当前状态。
- 修改定义或规则时重查受影响的证明；修改实例参数时重查相应实例；仅修改说明文字时检查文字与陈述一致性。构建系统管理依赖，不人工重复执行无关实验。
- 编译检查保证推导有效；有针对性的实例检查暴露边界问题；程序或硬件对应关系用各自的证据建立。三者不能互相代替。
- 完成证明不得依赖未证明占位或自定义硬件公理；检查定理及其依赖的公理，也检查量词、单位、非空实例和假设是否合理。
- 新增引理应服务已选定的组合结论。证明数量增长但组合结论没有前进时，停止扩写并检查问题定义。
