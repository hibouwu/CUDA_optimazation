# Lean 子项目协作规则

## 入口与范围

- 先读 `GOAL.md`、`ARCH.md` 和 `PLAN.md`，再读当前步骤相关的定义与证明。数学规范以 `ARCH.md` 为准，进度与阻塞只记在 `PLAN.md`。
- 第一阶段步骤 1–4 已完成。用户已授权后续目标模式：完成一条真实程序短链的事件/依赖映射、动态服务归约条件与测量口径核验，并评估第二阶段准入。每步先核对交付、前提与验收方式，完成后进行有具体依据的对抗性审查；失败则修正原有内容并复查。完整第二阶段实现及新 GPU 实验不在本轮范围；准入缺口须明确交付，不能以未经验证的假设冒充通过。
- 短链准入核验已完成。随后用户授权单独形式化 `wgmma_compute_step` 的计算服务递推与提交后延迟区间，并给出 `commit → compute_complete` 的局部图边依据；暂不扩展跨 CTA 输入网络。
- 第一阶段使用现有 coding agent，不建立 `tasks/`、`.runs/` 或额外编排框架，不开展证明工具对比评测。新增依赖须对应当前证明链的具体需要。

## 代码组织

- `GemmProofs/Core/Model.lean`：通用图、轨迹、观察完成时间、双侧合法性与秩证书。
- `GemmProofs/Core/Paths.lean`：路径下界与正权环无解。
- `GemmProofs/Core/Bounds.lean`：极值递推、可达性、夹逼、唯一性与不相容判据。
- `GemmProofs/Pipeline/Model.lean`：五事件图对通用模型的实例化及拓扑秩。
- `GemmProofs/Pipeline/Safety.lean`：槽安全、容量与占用下界。
- `GemmProofs/Pipeline/Examples.lean`：`S=1/4/6` 与 `22/21/17` 证明链。
- `GemmProofs/Pipeline/Compute.lean`：计算服务的代数递推、整数时间语义及局部图边区间证明，不依赖五事件实例的槽数或零偏移假设。
- `GemmProofs.lean` 为正式库入口；`Checks/Axioms.lean` 存放交付定理类型检查与公理审计；`scripts/check.sh` 为统一验收入口。
- 依赖方向为 `Core → Pipeline → Checks`；通用层不引用实例，检查模块不进入模型定义。保持唯一轨迹定义，不为不同性质另造状态类型。
- 工具链与依赖版本固定；使用外部 Lake 依赖时保留 `lake-manifest.json`。不预建无内容的目录或模块。

## 定理与定义的变更边界

- 实现前对齐交付定理的完整类型。类型检查应直接引用目标定理，明确参数、前提和结论，不通过额外假设或重新证明来绕过接口检查。
- 类型检查只能检验类型兼容性，不能检测同名定义内部含义的改变。修改图的边、合法性、观察集合、完成时间或参数域时，必须对照 `ARCH.md` 审查语义变化。
- 不得为通过检查而增加定理前提、削弱结论、改变模型定义或关闭验收项。发现规格问题时，在 `PLAN.md` 写明反例或阻塞并与用户讨论；普通辅助引理和保持语义的证明重构可直接推进。
- 定义、交付签名与验收规则经确认后，证明任务不自行修改其约定。确需调整时显式说明变化及影响，不把检查文件视为永远不能修正的文件。
- 若实现变更拦截，须对照明确的已确认基线，覆盖暂存与未暂存修改，并处理新增或缺失文件；普通 `git diff` 不能单独充当完整防篡改机制。

## 验证与交接

- 开始任务时先检查相关代码与已有验证记录；不把全量构建作为每次恢复上下文的固定步骤。文件或依赖变化、记录不足或出现错误时，运行对应检查。
- 开发时使用局部编译反馈；交付时执行统一验收。验收须覆盖正式库及 `Checks/Axioms.lean`，并将项目源码中的警告按失败处理。
- `#print axioms` 只报告依赖，不能自行拒绝额外公理。验收须显式检查每条交付定理的传递公理依赖，只允许 `propext`、`Classical.choice`、`Quot.sound` 的子集；出现 `sorryAx`、额外公理或检查缺失时失败。
- 最终交付不含 `sorry`，不以增加公理或跳过内核检查完成证明。未完成步骤如有临时占位，必须明确标为未完成，不能报验收通过。
- 在 `PLAN.md` 的相应步骤记录状态、必要的阻塞原因、下一步，以及最近一次有效检查的命令、结果和对应代码版本或差异范围。只保留影响后续工作的失败结论，不逐次记录 tactic 尝试。
- 编译结果说明代码是否通过检查；任务动机、尚未实现的目标及已否定路线由 `PLAN.md` 补充。完成汇报区分数学规范、Lean 已验证结果和硬件假设。
