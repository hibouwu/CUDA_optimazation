# 模型目标

更新：2026-10-20。本文件按三类模型拆分问题：每类先写要解决的问题，再细分子问题，逐项写输入、交付与验收。实机验证是三类模型共同的证据来源（第 4 节）；有效性、C1/C3 定义与研究规则见第 5 节。具体实验的选择与成绩见各计划和实验记录。

主要研究目标是通过实机逆向建立可执行的微架构假设（第 3 节）。规格基线和半经验模型并行保留，分别提供理想参照与现有预测水平；程序执行图与微架构规则是机制模型的组成部分。半经验模型用于对照，不作为机制模型的标准答案。

## 1. 规格基线

### 1.1 问题

给定程序需求与匹配的硬件规格，确定理想资源限制及其主导项。

### 1.2 子问题

| 子问题 | 内容 | 依据 |
|---|---|---|
| 需求计账 | 计算量 F 与声明存储层次上的流量 Q；理想流量、逻辑请求量与实际物理流量分别记录 | 程序需求 |
| 规格口径 | 匹配计算路径的峰值算力 P 与该通路的峰值带宽 B；精度、稀疏模式、缓存初态、频率与计时边界保持一致 | 硬件文档与规格配置 |
| 理想时间 | T_ideal = max(F/P, Q/B)，允许计算与搬运理想重叠，不含启动、有限并行度、依赖等待和排空 | 前两项 |
| 静态可行性 | 驻留、SMEM、寄存器等资源上限 | 静态执行信息 |

### 1.3 交付与验收

交付带假设的理想时间、限制项和静态可行性，计算入口见[规格基线计算](model/spec/spec_baseline.md)。验收核对需求、单位、边界与上限依据，不承诺实际耗时；与实测比较时只报告理想限制与实测的差距，不参加 C1、C3 的误差排名。

### 1.4 边界

只有 Q 是必要流量、服务率是对应条件下的可信上限时，结果才称时间下界，否则称条件化理想估计。实测与理想之差不直接命名为同步、排队或其他单一开销；不添加未知利用率或启动常数。

## 2. 半经验模型

### 2.1 问题

用当前数据给出实际时间预测，并作为机制模型的比较基线。

### 2.2 子问题

| 子问题 | 内容 |
|---|---|
| 工作映射 | 由静态配置与调度给出每个 CTA 的 tile 列表、波次、补齐与边界工作 |
| 阶段代价 | 供给、主循环、输出与交接的条件代价，参数为校准得到的有效值 |
| 执行组合 | cooperative／pingpong 的 CTA 递推，得到包络与关键 CTA |
| 有效频率 | 由形状、配置、输入描述与声明协议预测调用内的有效频率 |
| 时间映射 | 由包络到声明计时边界的完整时间映射 |
| 支持域 | 由校准覆盖决定的支持条件与拒绝规则 |

### 2.3 交付与验收

交付冻结的预测器、参数与支持域，现行版本见 [MODEL-CANDIDATES](model/semi_empirical/MODEL-CANDIDATES.md)。按 [C3](#53-c3-完整时间预测) 验证；有配置候选集合时另按 [C1](#52-c1-选配置) 验证。

### 2.4 边界

部分参数是多个过程合并后的有效代价，不对应明确的硬件对象；更换执行组织时参数未必可直接迁移，需要重新校准时记录成本。半经验与机制模型的预测一致不构成独立验证，在共享校准数据或假设时尤其如此。

## 3. 机制模型

### 3.1 问题

通过实机逆向建立可执行的微架构假设：辨识请求形成、资源共享、在途容量、仲裁、执行及完成释放规则，预测未参与建模的干预响应。局部机制可以独立交付，不以改善某个 GEMM 配置选择为前提。

程序执行建模负责表达操作、数据依赖、控制与同步、软件缓冲复用；微架构建模负责表达这些操作获得硬件服务的方式。两者组合后生成执行时间线，再检验完整时间和配置选择。软件依赖图、软件 stage 数与模型 L0–L4 层级不等于硬件内部拓扑、队列容量或硬件层级。

### 3.2 程序图

| 项 | 内容 |
|---|---|
| 问题 | 程序允许的操作及其推进条件 |
| 子问题 | 操作与事件（发出、就绪、消费、释放）；数据依赖、控制与同步；软件缓冲槽的代次与复用；tile 到 CTA、cluster 与 SM 的调度；各操作的资源需求 |
| 输入 | 源码、生成代码、执行语义与配置 |
| 交付与验收 | 经源码、生成代码与执行语义核对的操作和依赖图，入口见 [CUTLASS 程序图](model/mechanism/program/cutlass_program_graph.md)；图正确不代表硬件服务假设正确 |

### 3.3 硬件服务规则

问题：硬件服务的组织方式，以及限制请求推进的状态。按服务环节细分为以下子问题：

| 子问题 | 要区分的机制 | 可设计的探针变化 |
|---|---|---|
| 请求形成与服务粒度 | 软件请求转成服务需求的方式，以及可观察的拆分、合并或批次 | 请求大小、对齐、形状、地址关系与请求数量 |
| 发射与在途容量 | 发射间隔与未完成请求容量各自对推进的限制，以及容量的共享范围 | 独立请求数、发出间隔、依赖关系、发出者组织与消费者速度 |
| 计算执行与依赖 | 发射、执行服务、依赖等待与完成通知各自的约束 | 依赖链与独立操作流、操作形状、提交／等待组织 |
| 存储映射与共享 | 地址与访问者到服务资源的映射，以及发生共享或冲突的访问 | 地址／布局、广播关系、访问宽度及独立竞争流 |
| 仲裁与相互干扰 | 不同请求的争用方式、候选服务次序与公平性规则 | 请求类型比例、到达相位、来源组织、背景流与目标流 |
| 完成、可见性与释放 | 相同或分离的事件，以及各事件释放的容量 | 等待端点、观察端点、消费者延迟和后继请求的可推进时刻 |

交付首选与备选结构、状态转换、可辨识参数及适用域；按 [C2](#35-c2-机制主张) 检验，不要求先形成完整 kernel 预测。路径目录见[硬件规则](model/mechanism/hardware_rules/README.md)，模块级覆盖与实验接入见[微基准地图](model/mechanism/hardware_rules/MICROBENCH-ROADMAP.md)。

每项搬运研究必须声明源数据的实际分配／存放位置、源与目的地址空间、缓存初态及可能的服务层次、搬运指令路径、目的存储资源，以及完成／可见／复用端点。地址空间与物理资源分开：不能只写 GMEM→SMEM 就认定发生了 HBM→SMEM 传输，也不能用逻辑请求字节代替某一级的物理流量。资源参数维护在硬件文档，具体缓存准备和观察方法维护在实验任务中。

### 3.4 组合

| 项 | 内容 |
|---|---|
| 问题 | 程序依赖与硬件规则共同产生的执行 |
| 子问题 | 事件接口对齐；版本化服务规则接入程序图；逐项检查 stage、预填、输出相位等干预响应；完整时间 |
| 交付与验收 | 可执行事件模型及时间线；组合机制按 C2、完整时间按 [C3](#53-c3-完整时间预测)、配置选择按 [C1](#52-c1-选配置) 分别验收；未经验证的模块标为假设 |

### 3.5 C2 机制主张

| 项 | 定义 |
|---|---|
| 判断 | 一条可证伪的微架构或组合机制主张，并明确其属于硬件资源规则或程序与硬件交互 |
| 冻结前写明 | 主张的机制；至少一个竞争解释；能区分两者的干预；各解释对干预响应方向与幅度的预测 |
| 观测与标准 | 冻结前写定可观测量、适用范围与判定标准 |
| 判定 | 留出上主张的预测达到标准，且预先列出的竞争解释被区分性观测排除，才记为在声明范围内获得支持；不宣称机制唯一。证据无法区分解释时记为信息不足 |
| 边界 | 局部主张通过，不替代完整模型按事先承诺的全部指标进行的验收 |

证据暂不能区分的少量机制可以保留，选择当前最有依据的一个作为工作假设。记录选择依据、备选差异与重新研究条件；采用不等于通过，不可辨识的参数只保留组合量或范围。软件观察端点只能约束对应路径，不能直接命名内部硬件事件。

## 5. 共同定义与研究规则

### 5.1 有效性

模型有用，指它只用静态程序、冻结参数和声明的协议，对未测条件作出事先承诺的判断，并在冻结后的留出上达到预定标准。解释已有结果有开发价值，但不构成预测能力已经验证的证据。

模型承担 C1 选配置、C2 机制主张、C3 完整时间预测三项能力，分别判定。它们可复用程序、资源与事件描述；各服务的时钟口径分别保留，不预设所有成本随同一频率缩放。C2 可以只研究一条硬件服务路径，C3 误差小或 C1 选对均不能代替 C2 证据。

### 5.2 C1 选配置

| 项 | 定义 |
|---|---|
| 判断 | 给定算子、形状与候选配置集合，选出完整时间最短的配置 |
| 输入 | 各候选降级后的程序或 DAG、形状、输入数值描述、冻结参数、声明的调用历史与暖机协议 |
| 输出 | 各候选的预测时间，或足以确定排序的预测区间；选中的配置；同时报告周期预测 |
| 主要指标 | regret = 选中配置的实测时间 ÷ 候选中实测最短时间 − 1 |
| 辅助指标 | top-1 命中率、排序一致性 |
| 标准 | 每个形状 regret ≤ 待定；候选集合与形状范围在冻结前写定 |
| 基线 | 最佳固定配置（仅用校准数据选定，留出前冻结）、简单拟合、公开模型；分别记录各基线使用的校准数据。模型的价值体现为更低 regret、更广覆盖或更少校准 |
| 简化 | 频率等因素只有在声明范围内证明不改变选择、不突破 regret 标准后，才可省略 |
| 范围外 | 候选集合与形状范围以外的条件拒绝 |

### 5.3 C3 完整时间预测

| 项 | 定义 |
|---|---|
| 判断 | 给定程序、输入描述、设备与运行协议，预测约定起止边界内的完整时间 |
| 输出 | 时间点预测或预先定义覆盖要求的区间、支持域与拒绝项；机制模型另提供对应事件时间线 |
| 指标 | 绝对相对误差的中位数、尾部与最大值，支持率；区间预测另报告覆盖率和宽度 |
| 标准 | 具体阈值、条件集合与区间评分方式由任务在冻结前写定 |
| 比较 | 半经验与机制模型在共同支持条件上比较误差，同时报告各自全部声明条件的覆盖率、校准数据与成本 |
| 边界 | 目标及前序调用的实测时间、频率或内部事件只能用于单列诊断，不替代运行前预测输入；低时间误差不能证明机制成立 |

迁移另按未用于开发的程序组织、干预或硬件条件报告；需要专属重拟合时，记录新校准成本，不作为原模型直接迁移成功。

### 5.4 选题与优先级

<a id="current-scope"></a>

**2026-10-19 模块优先与逐级组合目标。** 近期依次完成两项交付：搬运、计算、同步／释放和输出的最小可执行模块包，以及用同一套规则闭合的局部链条：输入就绪 → full返回 → 计算完成 → WGMMA等待返回 → empty发布／槽释放 → producer再取得槽。模块分别用局部证据检验，连接用短／长链及S4/S6的响应检验；随后加入共享／竞争，最后进行完整cfg_b S6/S4验收。保留[九方向覆盖范围](model/mechanism/hardware_rules/MICROBENCH-ROADMAP.md#6-推进次序与本轮交付)，每方向完成一项有限、独立的机制检验。推进顺序为：固定真实程序事实 → 建立最小可执行模块 → 验证最小连接 → 加入共享与竞争 → 完整cfg_b S6/S4验收。参与cfg_b的规则接入同版请求级组合，推进原C2及C3独立验收。原12条件作为开发回归；C3沿用中位绝对相对误差≤5%、最大≤10%，正式验收使用冻结后未参与选择的新证据。普通L1/LSU等不参与cfg_b的路径独立验证后收口；寄存器和SM驻留先提供当前cfg_b所需的容量与启动依赖，进一步服务研究由具体缺口决定。首版九阶段接口及A–E测量保留为起点；当前安排见[PLAN §1](PLAN.md#1-近期顺序)。仅使用免费ROMEO，不修改历史／冻结结果的内容，不commit、不push；2026-10-20 按用户要求只调整了结果目录的存放位置（问题／合并实验），内容不变。

最小模块须交付明确的输入、输出端点、状态转换或复合规则、可独立运行的实现、局部证据与适用域；独立入口与组合共用服务规则，相同声明输入下的对应端点一致。未辨识部分保留显式工作假设及其检验条件。搬运模块以请求、地址、源状态及目的槽为输入，给出请求受理、输入就绪与占用释放；计算模块以指令序列、输入就绪及提交／等待组织为输入，给出提交准入、计算完成及等待返回；同步模块以就绪、计算完成及槽代次为输入，连接full返回、WGMMA等待返回、empty发布／槽释放和producer再取得槽；输出模块以输出操作、计算完成及源槽状态为输入，给出写入、源槽可复用及排空端点。真实GEMM从起点提供程序事实和工况。模块和局部连接的选择、定价与修正，以对应端点及干预响应为依据；近期优先补齐这些端点与状态。共享源和输出重叠用匹配的联合实验检验；完整GEMM时间残差在阶段5用于整体验收，并指出需要局部复查的连接。模块交付以组合所需的外部行为可执行、可单独检验为准，无需先完成全部内部微架构逆向。

阶段按已登记的有限交付收口，结论可以获得限定支持、被反证或信息不足；每项区分已完成的准备、实际测量和未解决的观测，准备完成不等于实测完成。局部阶段不以全部 C2/C3 通过为转段前提；需要新观测的部分保持未完成，其他不依赖该观测的工作继续。九方向按实际依赖推进，普通L1/LSU等独立路径的检验不作为完整cfg_b验收的前置条件。最终组合阶段须交付从声明输入到完整事件时间线及 plain 时间的同版模型、逐模块资格与假设、原条件和阈值下的评分报告；验收未通过照实保留，不用阶段交付代替验收通过。

### 5.5 继续与停止

继续研究一个未解释的现象，须同时满足：

1. 它的不确定性可能改变一项已承诺的判断：C1 的选择或 regret、C2 主张的判定、C3 的预测误差或支持范围；
2. 有望在有限成本内缩小这项不确定性。

不满足时，记录未解决问题与暂缓理由；支持范围的调整只适用于以后冻结的预测。现有可观察量不能区分解释时，写明缺少的辨识条件后停止。

已承诺的独立 C2 课题按本题的预算和终点推进，不因暂未改善 C1/C3 就撤销，也不因属于微架构研究就无限续期。程序图与验证工具任务须写明所支撑的能力，其实现检查不替代该能力的实机验收。

### 5.6 一轮研究

更新：2026-10-20，按用户要求简化。一轮研究对应一个合并实验中的一行记录。登记、执行与收口只要求以下四项：

| 项 | 内容 |
|---|---|
| 计划 | 问题、要改变的判断、固定与改变的条件、冻结预测与判定区间、条件数与重复次数上限 |
| 原始数据 | 测量输出与运行环境（GPU UUID、SMID、二进制或源码版本）；跨机器传输时附归档校验和 |
| 评分 | 从原始数据重算结论的脚本 |
| 结论 | 实验记录页轮次表中的一行：主张、条件、判定、证据链接；改变模型判断的事实写进该页“结论”节 |

不再要求逐文件输入绑定、异目录或新进程复放、身份审计、交付清单与收口文件；已有的保持原样。

判定区间按实测重复性确定：
- 用同批重复（至少 3 个独立进程）估计各量的离散，绝对量与响应（差值）分别给区间，区间不小于计时分辨率。
- 固定 5% 只作没有重复性数据时的默认值。

资格检查只作废受影响的进程或条件：
- 某个进程暖机不稳、桥接漂移或观察扰动超限时，剔除该进程并照实记录。
- 剩余数据仍能区分预列候选时照常判定，不能区分时记信息不足。
- 跨二进制的桥接失败时，改用同二进制内的对照判定。

默认上限为每轮最多 3 个候选、8 个开发条件与 4 个留出条件，每条件 3 个独立进程。2026-10-21、10-22 用户允许自主使用 GPU 资源，继续只用免费 ROMEO；每轮在计划中写定有限清单与执行时限，排队另记，执行中不扩展。实现故障先修共用执行器，再按同一计划重试。能由旧证据解决时不补测；新一轮须写明实质变化及其依据。

每轮须对应一个完整模型残差（C3）或已登记的 C2 主张；只为探针自身开销定价的轮次不单独立项。针对事先承诺的判断，结论记为通过、被反证或信息不足；预算用完仍不能判断时，只记“未解决”。

### 5.7 汇报

每轮结束报告三项：

1. 新增的可靠预测条件及其成绩；
2. 被排除的解释及其影响的模型选择；
3. 仍缺的信息及其将改变的决定。
