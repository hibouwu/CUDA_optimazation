## 资源与参数

### 计算资源引用

计算与片上资源引用 [L0](L0.md) 和 [L1](L1.md)；mainloop、epilogue 及缓冲状态关系统一见 [L2 通用模型](../../model/L2.md)。

### 存储与缓存容量

核对日期：2026-09-30，产品容量保留 NVIDIA 数据表的 GB 单位；CUDA 可见字节数与保留空间另记。HBM3 与 HBM3e 两列不能交叉配对。

| 存储资源 | 作用范围 | 官方产品容量或当前依据 |
|---|---|---|
| GPU HBM3 | 单 GH200 GPU 本地存储 | 96 GB；[官方数据表][datasheet] |
| GPU HBM3e | 单 GH200 GPU 本地存储 | 144 GB；[官方数据表][datasheet] |
| GPU L2 cache | GPU 共享 | ROMEO 实际设备：62,914,560 B（60 MiB）；[CUDA Runtime 查询](../../../../../results/gh200_resource_campaign/20261001-memory-c/device.jsonl)，不是全产品线保证值 |
| 硬件 L1 cache | 每 SM | 与 SMEM 的统一容量引用 [L1](L1.md#存储与缓存容量) |
| Grace LPDDR5X（按需） | CPU 本地存储，经 CPU–GPU 通路访问 | 120、240 或 480 GB；[官方数据表][datasheet] |

默认 GEMM 仍以 GPU 本地存储为边界；只有问题包含主机内存访问或传输时才增加 Grace 内存与 NVLink-C2C 需求，不能把两种存储容量或带宽直接合并。已有 ROMEO 归档的 CUDA 可见 GPU 内存为 95 GiB，设备名中的 120GB 不作为 HBM 容量，详见[设备状态](README.md#设备与参数状态)。

### 带宽与数据搬运

本节保存全局路径的资源参数；操作语义与完成事件统一见 [L0 数据搬运操作](L0.md#数据搬运操作)。按[资源 ID 与计账约定](../../model/interfaces.md#3-共享资源)引用参数，资源共享范围不因本层调用次数而复制。

| 访问路径 | 范围与方向 | 服务参数及约束 |
|---|---|---|
| HBM 访问 | 外存读写；多 SM 共享 | 实际外存流量、延迟、读写混合带宽 |
| L2 cache 访问 | 多 SM 共享的缓存通路 | 实际流量、命中条件、读写联合限制 |
| 普通 global load/store | GMEM ↔ 寄存器，按缓存策略区分 | 访存合并、缓存命中、指令发射与数据服务；输入输出分别计量 |
| TMA 搬运 | 按所选指令的方向区分；片上端引用 L1 | payload、stride、对齐、描述符、布局、延迟及在途请求条件 |
| cluster / DSM 通路（按需） | 协作 CTA 间跨 SM 访问 | 仅使用该通路时增加流量、带宽与完成依赖 |
| local 访问（按需） | 线程私有地址空间，经实际缓存到设备内存 | 计入 spill、栈和局部数组的事务；复用本表存储与带宽 |
| TMA multicast（按需） | 一次源请求向 cluster 内指定 CTA 的 SMEM 分发 | 分别计源请求、各目标写入及跨 SM 服务；不按接收 CTA 数直接复制 HBM 流量 |
| 参数、标量与描述符访问（按需） | `.param` / `.const` / `.global` 等实际位置 | 计入访问需求与状态；tensor-map proxy 不新增一份 HBM 带宽 |

普通 global 路径已有 CUDA 12.9 条件化测量，见[EXP-02](../../experiments/gh200_sm90/EXP-02-memory-paths.md)与[原始报告](../../../../../results/gh200_resource_campaign/20261001-memory-c/REPORT.md)。grid 为 4×132 CTA、256 线程/CTA、每线程 16 B 访问；工作集按完整 CTA 轮次向上对齐。下表为 **GB/s 请求 payload/GPU**，由全网格 globaltimer 完成窗口计算，不能解释为物理 HBM 或缓存带宽。

| 访问配置 | 实测中位数（GB/s） | 计量与限制 |
|---|---:|---|
| 8 MiB 请求工作集，`.ca` 读 | 13127.090 | 多次重复读取；未证明命中层级 |
| 8 MiB 请求工作集，`.cg` 读 | 7739.437 | 同上，缓存策略不同 |
| 256 MiB 请求工作集，`.cg` 读 | 3514.280 | 输入地址和 checksum 开销在窗口内 |
| 256 MiB 请求工作集，`.wb` 写 | 3824.902 | 包含 device fence；不证明物理写回流量 |
| 各 128 MiB 请求工作集，1:1 读写 | 3392.663 | 读与写 payload 合计，不是每方向分别该值 |

每配置 10 次独立进程，误差范围和 CV 见报告。独立读、写服务不能默认同时达到；GMEM 请求量与实际 HBM 流量分别计量。TMA、DSM 和方案匹配的联合服务仍待测。

### 官方带宽规格

| 访问对象或通路 | 单 GH200 产品标称值 | 适用条件与来源 |
|---|---|---|
| GPU HBM3 | 最高 4 TB/s | 与 96 GB HBM3 产品档配对；[数据表][datasheet] |
| GPU HBM3e | 最高 4.9 TB/s | 与 144 GB HBM3e 产品档配对；[数据表][datasheet] |
| Grace LPDDR5X，480 GB 档 | 最高 384 GB/s | CPU 本地内存带宽；[数据表][datasheet] |
| Grace LPDDR5X，120/240 GB 档 | 最高 512 GB/s | CPU 本地内存带宽；[数据表][datasheet] |
| NVLink-C2C，CPU ↔ GPU | 双向合计 900 GB/s；单方向 450 GB/s | [数据表][datasheet]与[架构白皮书第 12–14 页][whitepaper] |

TB/s、GB/s 按十进制速率读取。读写混合、TMA、跨缓存访问与 CPU–GPU 远程内存访问的有效带宽仍需相应服务模型；不能把 HBM 产品带宽同时赋给每个 SM，也不能将 C2C 的双向值当成单向速率。GH200 NVL2 的双 GPU 汇总值不用于本单 GPU 模型。

### TMA 请求、描述符与完成条件

以下为 SM90 普通字节存储类型的 tiled TMA 约束；采用 `interleave=NONE`。依据 [CUDA Tensor Map API][tensormap-api] 与 [PTX tensor copy][tensor-copy]，不把较新架构的 sub-byte 搬运形式或新的 swizzle 形式引入 GH200。

| 对象 | 已确认约束 | 建模用途 |
|---|---|---|
| tensor-map | 128 B 对象，API 要求对象地址 64 B 对齐 | 记录描述符的存储位置、创建/更新及可见条件 |
| tensor 维度 | rank 为 1–5；各全局维度为正，最多 \(2^{32}\) | 是描述符范围，不是 CTA tile 数量 |
| 全局地址与 stride | 基址 16 B 对齐；编码的外层 byte stride 为 16 B 的倍数且小于 \(2^{40}\) | 不满足时需换路径或由方案计入布局适配成本 |
| 单次 box | 各维 1–256 个元素；最内维字节数是 16 B 的倍数 | 超过单请求范围的 tile 需分解请求，不能仍按一次 TMA 计数 |
| element stride | 各维 1–8；该无 interleave 模式不支持对最内维作独立跨步遍历 | 用实际请求及有效元素数计量 |
| SMEM 布局 | 选择与目标支持相符的 none/32/64/128 B swizzle，并满足内维宽度、地址对齐和布局约束 | 消费者与搬运写入的布局必须一致；swizzle 不新增存储资源 |
| tensor copy 的 SMEM 端 | CC 9.0 多维 bulk tensor copy 要求 SMEM 地址 128 B 对齐，barrier 地址 8 B 对齐 | 与下面普通 1D bulk copy 的 16 B 要求区分 |
| 1D bulk copy | byte size 为 16 B 的倍数，源和目标地址 16 B 对齐 | 与 tensor-map 形式分开，不混用两者所有约束 |

SMEM 端对齐见 [CUDA TMA 对齐表][tma-alignment]；swizzle 的 base offset 与消费者索引仍须一致，不能仅凭地址对齐认定布局正确。global→SMEM 的 `mbarrier::complete_tx::bytes` 与 SMEM→global 的 bulk-group 使用不同完成机制，具体事件见 [L0](L0.md#异步分组完成与在途条件)。尤其是输出侧 `.read` wait 不能代替 GMEM 写完成。[bulk copy][bulk-copy]、[bulk wait][bulk-wait]

描述符在 host 上准备是否计入时间，遵循问题声明的边界；计时开始时若假定已就绪应写入运行条件。kernel 内的坐标更新、描述符访问、必要 proxy fence 或布局适配仍按实际路径计账。

### Cluster、DSM 与多播通路

| 机制 | 已确认的硬件边界 | 需求与共享条件 |
|---|---|---|
| DSM | cluster 内 CTA 可读写或原子访问彼此 SMEM | 容量由各 CTA 的实际 SMEM 分配组成，没有额外 DSM 容量；请求完成前相关 CTA 和存储必须存活 |
| TMA multicast | 在同一 cluster 内选择接收 CTA，写入各接收方对应 SMEM 偏移 | 同时记录源请求、接收端存储与完成通知；源端复用不能消除目标端写入 |
| cluster 同步 | 协调参与 CTA 的就绪、远程访问完成及退出 | 不替代各异步路径自己的完成条件；驻留与调度约束见 [L3](L3.md#cluster-驻留与调度) |

来源：[Hopper cluster/DSM][hopper]、[CUDA DSM][dsm]、[PTX 多播][tensor-copy]。多播不保证任意布局下固定倍数的带宽收益；当前没有 DSM/TMA 多播的服务率数据。这里的 cluster 是单 GPU 内部协作，属于当前范围，与暂缓的 Distributed GEMM 不同。

### 缓存与共享服务状态

| 参数或条件 | 当前依据 | 处理方式 |
|---|---|---|
| 本机 GPU L2 cache 容量 | CUDA Runtime 返回 60 MiB，见[设备记录](../../../../../results/gh200_resource_campaign/20261001-memory-c/device.jsonl) | 按已测设备身份使用，不套用 H100 容量 |
| L1/L2 的读写服务与命中状态 | 已测普通 global 请求吞吐，实际缓存流量/命中率未证明 | 普通 global、local 与 TMA 分别记录经过的路径；不将 GMEM payload 当作 HBM 字节数 |
| HBM 混合读写、多个 SM 并发 | 已有 1:1 global 请求混合服务；物理 HBM 流量未证明 | 使用联合服务参数，不能让各 CTA 分别获得整卡峰值 |
| TMA 请求启动与在途容量 | 已有 ISA 规则，缺条件化服务数值 | 按方向、box、并发与完成机制保留符号；不由 SMEM stage 数推出 |

可选的压缩、缓存持久化或远程内存路径，仅在运行条件或方案声明使用时扩展；不能无条件假定其收益。[Hopper 内存系统][hopper]

## 待确定参数
