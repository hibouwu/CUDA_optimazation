## 资源与参数

### 计算资源引用

计算操作的硬件参数引用 [L0](L0.md#计算资源)，不另列一份吞吐上限。

### 存储与缓存容量

官方架构参数按 CUDA 13.1 CC 9.0 记录；表中的 KB/K 是 1024 单位，本文统一写成 KiB 或寄存器个数。

| 资源 | 作用范围 | 官方容量或上限 | 来源 |
|---|---|---|---|
| 寄存器文件 | 每 SM | 65536 个 32-bit 寄存器，即 256 KiB | [CUDA 规格表 31][cuda-spec] |
| SMEM | 每 SM | 最大 228 KiB | [CUDA 规格][cuda-spec]、[Hopper 指南][hopper] |
| SMEM | 每 CTA | 默认/静态分配上限 48 KiB；显式 opt-in 的最大分配 227 KiB | [CUDA 规格脚注][cuda-spec]、[Hopper 指南][hopper] |
| 硬件 L1/纹理缓存与 SMEM 统一空间 | 每 SM | 256 KiB，与 SMEM 共用 | [CUDA 规格表 32][cuda-spec] |
| SMEM bank | 每 SM 的共享内存组织 | 32 个 bank | [CUDA 规格表 31][cuda-spec] |

SMEM carveout 可选 0、8、16、32、64、100、132、164、196、228 KiB；它改变统一空间中 SMEM 与缓存的分配，不能将 256 KiB 与 228 KiB 再相加。CUDA 为每 CTA 保留 1 KiB SMEM，具体分配与驻留仍按 runtime 条件核对。[CUDA 规格][cuda-spec]、[Hopper 指南][hopper]

### 寄存器分配与溢出

以下舍入规则来自本机 CUDA 13.0 官方 SDK 的 [cuda_occupancy.h][occupancy-header]：`cudaOccRegAllocationGranularity`、`cudaOccSMemAllocationGranularity`、`cudaOccSubPartitionsPerMultiprocessor` 及两个 `cudaOccMaxBlocksPerSM*Limit` 函数。它们是工具链的 occupancy 计算依据，不是本次设备实测；不改写已有 CUDA 12.9 复测记录。

| 分配对象 | CC 9.x 规则 | 模型中的使用方式 |
|---|---|---|
| 每 warp 寄存器 | 按 256 个 32-bit 寄存器向上舍入 | 先乘完整 warp 的 32 个线程，再舍入；不能仅用有效变量的字节数 |
| 寄存器子分区 | occupancy 模型按 4 个子分区/SM 核算 | 还需检查子分区可容纳 warp 数和 CTA 启动约束；不能只做整 SM 总量除法 |
| 每 CTA SMEM | 静态、动态与系统保留量之和按 128 B 向上舍入 | 计入 barrier、padding 与编译器增加的对象；SMEM carveout 另约束可用总量 |

以普通固定寄存器配置为例，令 \(r\) 为编译后每线程寄存器数、\(n_t\) 为 CTA 线程数：

\[
R_w=256\left\lceil\frac{32r}{256}\right\rceil,\qquad
R_{\mathrm{CTA}}=R_w\left\lceil\frac{n_t}{32}\right\rceil.
\]

SDK 的每 CTA 启动检查还使用按 4 个子分区舍入后的 warp 数；上式不是完整 occupancy 公式。SMEM 核算为：

\[
S_{\mathrm{alloc}}=128\left\lceil
\frac{S_{\mathrm{static}}+S_{\mathrm{dynamic}}+S_{\mathrm{reserved}}}{128}
\right\rceil.
\]

\(S_{\mathrm{reserved}}\) 由设备条件给定；Hopper 文档记录为 1 KiB/CTA。227 KiB 是用户 SMEM 上限，不能再从该用户上限重复扣除保留量。实际驻留采用目标设备与 kernel 属性核算，可对照 [CUDA occupancy API][occupancy-api]。

| 情形 | 硬件或工具链条件 | 资源归属 |
|---|---|---|
| 普通寄存器分配 | 变量最后一次使用不自动归还 CTA 的寄存器配额 | 生存期复用影响编译分配，驻留按实际分配量判断 |
| `setmaxnreg` | `sm_90a`；目标计数为 24–256、8 的倍数；warpgroup 一致执行；`.inc` 可能等待 CTA 池中空闲寄存器 | `.dec` 归还 CTA 内部池，不能视为直接释放给另一个 CTA；256 是该指令的配额操作数允许值，不改写常规每线程寄存器上限 |
| 默认 local 路径 | 溢出、局部数组或栈可能使用 `ld.local` / `st.local` | 线程私有地址空间，复用实际缓存与外存；没有新增一份片上容量 |
| 可选 SMEM spilling | CUDA 13.0 起可显式启用，受编译模式和适用条件限制 | 增加既有 SMEM 分配与访问需求；当前 CUDA 12.9 复测不采用此功能 |

依据：[CUDA 寄存器管理][registers]、[setmaxnreg][setmaxnreg]、[local memory][local-memory]、[SMEM spilling][smem-spill]。当前代表微基准在启动前检查 `localSizeBytes`；没有溢出路径的性能测量。模型若限定无溢出，需在方案中明确适用条件，而非把超量需求当成零成本。

### 带宽与数据搬运

| 访问路径 | 方向或参数来源 | 本层描述的量 |
|---|---|---|
| 线程读取 SMEM | SMEM → 寄存器 | 字节数、访问宽度、有效带宽与 bank conflict |
| 线程写入 SMEM | 寄存器 → SMEM | 字节数、访问宽度、有效带宽与 bank conflict |
| 计算指令取数 | 引用 [L0 数据供给需求](L0.md#数据供给需求) | 继承已计入的访问需求；本层补充同时访问时的竞争 |
| `ldmatrix` / `stmatrix` | SMEM ↔ 寄存器片段；指令约束见 [L0](L0.md#数据搬运操作) | 矩阵形状、bank 事务、发射与实际服务；不能直接套用普通 load/store 测量 |
| warp 内交换 | `shfl.sync` 的寄存器数据交换 | 指令需求、依赖与发射竞争；服务数值待定 |

各路径使用 [L0 数据搬运操作](L0.md#数据搬运操作) 的事件定义；本层保留片上资源参数，并根据线程/数据映射推导访问需求。各路径记录独立访问与同时访问的条件。线程 SMEM load/store 带宽不能替代 Tensor Core 取数或 TMA 写入 SMEM 的带宽。

普通 SMEM scalar 路径已有 [EXP-02](../../experiments/gh200_sm90_archive/EXP-02-memory-paths.md) 条件化测量：单 CTA、256 线程、32 KiB 分配，每轮每线程 8 次 `ld/st.volatile.shared.u32`，循环与 CTA 同步包含在内，读路径还包含 checksum 累加。单位为 **请求 B/clock64 cycle/CTA**。

| 访问配置 | 实测中位数 | 适用条件 |
|---|---:|---|
| 读取 stride=1 | 115.633 | 范围 88.048–115.633，CV 12.41%；待稳定性复测，不能固定为单一带宽参数 |
| 读取 stride=2/4/8/16/32 | 63.981 / 31.996 / 15.999 / 8.000 / 4.000 | 指当前地址映射的请求吞吐；分配大小不等于每轮独立访问量 |
| 写入 stride=1 | 127.919 | 无重叠写地址；包含循环和 CTA 同步 |

每配置 10 次独立进程，完整分布见[报告](../../../../../results/gh200_resource_campaign/20261001-memory-c/REPORT.md)。这些值不替代 `ldmatrix/stmatrix`、Tensor Core 取数或 TMA 写入服务，也不代表 SMEM 物理上界。结果写入 SMEM 仍仅在输出接口要求时计入。

### 驻留与指令发射

| 驻留约束 | CC 9.0 官方上限 | 来源 |
|---|---:|---|
| 每 warp 线程数 | 32 | [CUDA 规格表 30][cuda-spec] |
| 每 CTA 线程数 | 1024 | [CUDA 规格表 30][cuda-spec] |
| 每 SM 驻留 warp 数 | 64 | [Hopper 指南][hopper] |
| 每 SM 驻留线程数 | 2048 | [CUDA 规格表 30][cuda-spec] |
| 每 SM 驻留 CTA 数 | 32 | [Hopper 指南][hopper] |
| 每线程寄存器数 | 255 个 32-bit 寄存器 | [CUDA 规格表 31][cuda-spec] |
| 每 CTA 寄存器数 | 65536 个 32-bit 寄存器 | [CUDA 规格表 31][cuda-spec] |

实际驻留由线程、寄存器、SMEM 和所选协作方式共同限制；分配舍入见上表，实际 kernel 的寄存器数、动态 SMEM 和子分区限制另行代入。一个 warpgroup 不等于一个完整 SM。

warp 调度、访存发射及辅助指令的有效服务与共享关系仍待确定；操作需求按 [L1 发射接口](../../model/L1.md#驻留与指令发射)给定。

### 同步约束

| 同步机制 | 关联对象 | 本层约束 |
|---|---|---|
| CTA barrier | 参与同步的线程 | 到达条件与等待时间 |
| `mbarrier` / 异步完成通知 | 输入缓冲、搬运与消费者 | 使用输入前等待搬运完成；复用缓冲前等待消费者完成 |
| WGMMA 完成等待 | 累加状态与计算结果 | 引用 L0 完成事件，确定读回和存储复用时刻 |

| 同步对象 | 容量或存储规则 | 适用边界 |
|---|---|---|
| `barrier.cta` / `bar` 的命名 barrier | 每 CTA 16 个编号，0–15 | 不能据此推导每 SM 的独立吞吐或所有同步对象的数量上限 |
| `mbarrier` 对象 | 8 B、8 B 对齐，存放在 SMEM | 按对象数量计入 SMEM；不占用上述 16 个命名编号 |
| `mbarrier` 完成状态 | 当前 phase 的 pending arrivals 与 tx-count 均归零才完成 | 跟踪的单位依异步操作而定；TMA 的 bytes 完成机制按字节计数 |

来源：[命名 barrier][barrier]、[mbarrier 对象][mbarrier]。这些是对象数量、存储和完成语义，不能推出同步操作的延迟或吞吐量。

软件缓冲及同步状态占用上述存储资源，不单独增加容量。TMA 路径见 [L0](L0.md#数据搬运操作)，全局路径参数见 [L2](L2.md#带宽与数据搬运)；输入供给与缓冲复用的组合关系见 [L2 通用模型](../../model/L2.md#流水线状态与同步约束)。

## 待确定参数

容量、分配舍入及同步对象规则已列出。普通 SMEM scalar 路径已有上述限定配置的吞吐；实际 kernel 占用、矩阵搬运/寄存器交换路径的延迟与带宽、发射和混合操作联合服务仍待确定。L0 计算复测不能分离出独立 SMEM 带宽。
