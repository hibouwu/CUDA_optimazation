# EXP-11：同步、到达偏斜与完成事件

状态：A 草案，待独立审查；没有探针、设备运行或性能结果。

## 实验问题与最小例子

一个 CTA 的 128 个线程完成一次 barrier，工作量记为一次集合同步阶段，不是 128 次独立阶段。若循环 2048 轮，每轮八次 rendezvous，共 16,384 个阶段，CTA 周期差除以 16,384，得到该条件下的平均 cycles/phase。它包括循环和同步的服务开销。

让最后一个 warp 在每次到达前多做固定工作，会同时增加计算与等待。两组总时间之差不能直接叫作 barrier 自身延迟。本实验分别保留无额外工作、固定工作及实际到达诊断，解释多出来的时间属于什么边界。

## 有限配置矩阵

| 对象 | 参与线程 | 到达条件 | 点数 |
|---|---|---|---:|
| warp barrier | 32，完整 mask | 无额外工作 / 后半 warp 固定工作 | 2 |
| CTA barrier | 128、256 | 无额外工作 / 最后一个 warp 固定工作 | 4 |
| `mbarrier` arrive/wait | 128、256 | 同上 | 4 |
| CTA/GPU acq_rel fence、async proxy shared fence | 32 | 无待完成请求，重复发出 | 3 |

总共 13 点，均为单 CTA。barrier 每点 2048 轮，fence 每点 8192 轮，每轮八个操作位置。固定工作为 256 次保留依赖的 `mad.lo.u32`，按 32 位模运算核对最终值。

合同见 [synchronization.json](../../../../../microbench/gh200_resource_campaign/contracts/synchronization.json)。不在本阶段测所有 fence scope，不把 DSM cluster barrier 混入 CTA barrier。

## 计时与完成条件

CTA 入口使用 barrier 0，记录起点后再次同步，正式循环的 CTA barrier 使用编号 1。最终结果写入可检查的位置，经 CTA barrier 后再取终点。原始周期来自同 CTA；诊断中也记录 SM 身份。

`mbarrier` 使用 8 B 对齐对象，由线程 0 在窗口前初始化，expected arrivals 为 CTA 线程数。每线程每阶段 arrive 一次，用自己返回的 state 等待完成。等待循环设有限超时，记录尝试次数；不能预设每阶段恰好只发出一次 wait。所有线程退出最后阶段且 CTA 同步后才 invalidate。

固定工作组的主计时包含该工作、同步和等待。另用独立诊断 launch 记录一次操作的逐线程到达及离开时间，展示实际偏斜。编译器的汇合行为可能改变偏斜，因此配置了额外工作并不自动证明出现了预期到达差。逐阶段诊断时间戳不放入正式性能循环。

三个 fence 配置只描述无待完成请求条件下的发出服务。最终 CTA barrier 是额外的显式完成条件；fence 不被当作 `cp.async`、TMA 或 WGMMA 全部完成的证明。

## 正确性和审查

独立正确性路径每阶段先写入 seed、线程和阶段可识别的数据，执行目标同步后读取相邻参与者的数据，再执行一次同步，防止下一阶段覆盖仍在被读取的数据。所有线程的结果和阶段数都需核对。fence 的数据消费验证使用明确的参与者同步，不借一次计时声称证明整个内存模型。

CPU 检查覆盖模运算、阶段计数及错误参与数/工作量负例。B 阶段核对真正留在循环中的同步指令、固定工作依赖、初始化位置和等待循环，再运行有限时间的 GPU 数值预检。上述正确性路径与性能循环的差异必须在结果中列明。
