# GH200 实验执行规范

实验问题、条件和模型目标见 [PLAN](PLAN.md)。本文件维护对话分工、公共代码、数据同步、Slurm 运行与验证冻结流程。

实施方案更新：2026-10-09。**目标模式已启动，三组离线结果已集成，公共框架已完成首批 GH200 检查；具体结果和下一批任务见[当前状态表](#status)。** 默认采用一个管理对话、三个执行对话，最多三个独立 GPU 计时流；实际并发按账户额度、节点与存储余量调整。PLAN 中“共享 GPU 的计时串行”仍成立，不限制不同独立分配之间并行。

## 1. 管理对话与工作分配

**唯一管理者是提出并维护本计划的对话，实际 thread ID 只在[当前状态表](#status)登记。** 下文“本管理对话”均指该条目，不是任意打开文件的新对话。它负责公共 cfg_a/b/c 测试框架、分派、Git 集成、资源总量、最终模型和 V01/V09，不自动把管理权交给历史验收对话。执行对话名称下表只是拟用名，有合适的已有对话则复用，否则再创建。

| 对话 / agent | 首轮负责的原实验 | 首先完成的离线工作 | 后续 GPU 工作与交回内容 |
|---|---|---|---|
| 管理：本对话 | PLAN、README、RULES、共同接口、组合模型、V01/V09 | 固定本轮范围和源码基点，一次性集成公共开关，整合 A/B/C 候选；检查窗口、单位与重复计账 | 组织参考卡校准和自动冻结，展示 V09 确认包，获用户确认后采样并统一评分 |
| A：GH200 供给与请求 | R10、R13、EXP-15/16；必要时 R03、B01 | 用 V08 校准与 84 个后续条件中的可比记录拟合有效供给；区分计算受限点与供给受限点，列最小缺口 | A/B 行距、多播配对、活动 SM、stage；交回条件服务函数、残差、适用范围及新组织验证 |
| B：GH200 输出与边界 | R15、R18、R19 | 拟合输出候选；检查补齐 tile；从 V06/V07/V08/R18 记录分析入口、SMID、输出重叠和最后完成者 | 输出并发、必要的边界配对和 cluster 派发；交回事件关系与周期修正 |
| C：GH200 时间与输入 | R09；复用 V03 与原 R07 的证据 | 对齐 S/预填/完整完成端点，核对频率残差、输入生成与暖机，准备共同参照 | 用公共 cfg_a/b/c 框架做长窗口、三档输入和正式时间测量；旧 R09 探针仅作机制对照 |

首轮不同时开 25 个执行任务。A/B/C 可以并行完成第 0 步；只有本组代码、检查和最小条件已经就绪，才申请本组 GPU，不占着分配等待另一组写代码。

主线稳定后继续使用这三个执行对话轮换任务，不叠加更多管理层：A 承接 R03、EXP-12、B01、EXP-13/17 的存储扩展；B 承接 R11/R12/R14 与真实组合片段；C 承接 R01/R02/R06/R16 及相应 EXP 指令族。共同参照完成后，C 也可先准备 RF 的离线/SASS 对照，不必等待所有主线 GPU 结果；同一时间每组只有一个明确的小目标。

执行对话之间可以读取已交回的结果，不直接修改对方工作。单项完成不代表整轮预测通过，只有管理对话更新公共状态。这里不恢复旧 A/B/C 多层验收流程；管理者复核关键计算、差异和证据即可，出现具体争议再做针对性复核。

## 2. 代码怎样并行修改与合并

每个长期执行对话使用独立 Git worktree；同一目录下的临时子 agent 只用于有明确边界的读取/分析，不代替三个具有独立目标的执行对话。[Codex worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)说明了独立 checkout 的用途。

1. **先固定共同基点。** 执行启动时，管理对话先检查当前未提交修改，将已确认的本轮文档整理提交到本轮集成分支，记录 BASE_SHA；无关用户修改不夹带。创建 worktree 前确保它们包含同一版 PLAN。不能直接从旧 HEAD 分支后误以为已有未提交计划会自动带过去。
2. **建议分支名。** 集成为 gh200-mechanism-integration；三个执行分支为 gh200-supply、gh200-output-boundary、gh200-clock-input。它们是拟用名，创建前检查是否已有对应工作，存在则复用其真实进度。
3. **各组只提交自己完成的改动。** 文档、探针、配置和分析器按小的可复核单元提交，交回提交 SHA 与验证命令；不向 main 直接提交，也不强制推送。大原始数据沿用 results 归档，不塞入代码提交。
4. **管理者串行集成。** 检查工作基点与写入范围，逐组 cherry-pick 或合并到集成分支，处理真实冲突并运行受影响的 CPU/SASS/小规模检查。集成方式选一种，不对同一提交同时合并和 cherry-pick。
5. **变更共同依赖时同步一个明确版本。** 管理者公布新的集成 SHA，执行组在干净工作树上合并该版本；有未提交工作先保存本组提交，不 reset 或 stash 他人的修改。已经冻结的运行包保持不动；下一批使用新 SHA、新 run-id。

按下面的范围保持单一维护者：

| 文件或对象 | 首轮维护者 | 其他组如何提出修改 |
|---|---|---|
| R10/R13、EXP-15/16 的专用探针、分析与条件配置 | A | 可提出公共框架补丁，不能自行维护另一份 cfg_a/b/c 框架 |
| R15/R18/R19 的专用输出片段、条件配置与分析；run_r19.py 等专用包装入口 | B | 公共框架由管理者维护，B 只改本组专用部分 |
| R09 分析、r09_run/analyze/probe 与独立覆盖头 | C | 旧 128×256×64、4 stage 探针只作机制对照；正式频率与时间换算从公共 cfg_a/b/c 框架取数 |
| r18.cu、r18_trace.hpp、run_r18.py、run_v08.py 的公共构建/校准逻辑，以及 V09 验证入口 | 管理对话 | A/B/C 提交小补丁或参数需求，管理者合成一个公共提交，三组更新到同一 SHA |
| r00_common.hpp、gaps_common.hpp、v06_trace.hpp、共享 CUTLASS 覆盖/构建逻辑、公共输入检查 | 管理对话 | 输入生成、容差和公共打点在同一版本实现，不能各组复制变体 |
| PLAN、EXECUTION、两个 README、RULES、模型接口与最终预测/拟合入口、V01/V09 | 管理对话 | 执行组交回短结论和代码，不自行维护第二份总表 |
| 原 frozen、旧 run、families 中冻结源码 | 只读 | 新分析写独立 reanalysis 子目录，新采样写新 run-id |

分工以具体文件为准。run_v08.py 与 run_r18.py 都编译 r18.cu，B01 的缓存入口也复用 run_r18.py；这些是跨组公共依赖，不能归某个实验组独占。专用包装入口若开始承担共享行为，先由管理者明确归属，再修改。

### 第 0 步共同准备 cfg_a/b/c 框架

管理者汇总 A/B/C 的需求并在维护源码中一次性准备以下开关，保留默认模式；旧运行包中的源码和冻结预测不改。第 0 步完成接口、代码和 CPU 检查，首次 GPU 分配先完成小规模数值/SASS/资源核对，再开始正式采样，不把尚未运行的检查写成已通过。

| 公共能力 | 最小要求 | 使用者 |
|---|---|---|
| sm_count | 默认仍为全部 SM；合法非默认值写入 KernelHardwareInfo，核对 cluster、grid 与资源约束，保存实际 grid 和逐 CTA SMID/窗口 | A 的活动 SM 扫描，C 的少量 SM 频率对照 |
| 输入模式与 seed | 现有 dyadic、全零、固定种子随机有限 FP16；保存分布/seed，初始化与正确性检查在目标计时外 | C 主导数值定义，A/B 使用同一实现 |
| 正确性模式 | dyadic 保留原检查，随机输入使用明确容差和独立参考；全零与随机样本不能借用旧 dyadic 参考 | 三组与 V09 |
| cfg/几何/行距/缓存准备 | cfg_a/b/c、M/N/K、A/B/D pitch 和暖机协议显式保存；长窗口按实际时间分组，不只按 K 标签判断 | A/B/C |
| 计时与冻结信息 | plain/stamped/ends、事件定义、GPU UUID、源码/构建/参数身份一致；新增打点单独检查扰动 | 三组、V01/V09 |

管理者发布 HARNESS_SHA。三组依赖它准备自己的条件；共同开关变化后再发布一个版本，已经采样的 run 不覆盖。默认条件检查既核对结果，也核对 SASS、寄存器和 SMEM；发生变化就报告影响，不能以“只加一个开关”为由自动沿用旧参数。

当前 HARNESS_SHA 为 **6338653**。[job 738097 的检查记录](../../../../../../results/gh200_resource_campaign/access_rules/20261009-R09-R13-shared-smoke-job738097/check_outcomes.json)覆盖三配置的 plain/stamped/ends：M=2304、N=3072、K=1024 下三档输入及 dyadic 的 SM32 共 36 个进程通过，全部 4096 点已独立回放；SM32 的六份 trace 均有 32 个不同 SMID、峰值 32 个 CTA 窗口重叠。九个二进制的 HGMMA 数、168 个寄存器、spill 状态与 V08 一致，stage/SMEM 未变。额外的 64×64×65536 随机检查三配置均超出初定容差（最大约 3.07 倍），保留为失败；长 K 随机输入尚不能直接用于正式批次。该作业为共享节点上的正确性检查，不提供性能参数。

C 继续负责 R09 的分析与解释，但进入 V09 的时间换算必须来自公共框架的 cfg_a/b/c、实际输入模式和计时边界。旧 r09_probe.cu 的 128×256×64、4 stage 只回答时钟、预填、打点等机制问题，不能把其拟合常数直接移植给 cfg_a/b/c。

## 3. 数据怎样共享，怎样防止覆盖

- **本地唯一归档位置**继续使用本项目 results/gh200_resource_campaign/access_rules。旧归档所有组只读。worktree 中 Git 忽略的 results 不会自动出现；分析时显式传入主 checkout 下的绝对输入路径，不给每个 worktree 复制一整份历史结果。
- **每个运行目录只有一个写入者。** 采样包由所属执行组产生，命名中带原实验编号、job ID、版本；GPU UUID、源码提交及二进制身份进入该 run 的既有元数据。不同 GPU、源码或测量协议使用不同 run-id，不能为凑齐试次数拼成同一组。
- **离线输出也分开。** 旧数据上的分析写该 run 的 reanalysis/<组名-日期-版本>，不覆盖旧 summary/预测/评分。其他组读取前先确认分析已经结束；不能读一半写入的 JSON。
- **远端按包隔离。** 在经配额确认可用的 /scratch_p/<登录名>/gh200/<组名>/<源码SHA-批次>/ 下准备本批源码与结果；不向历史超额的项目目录追加，不覆盖另一个作业正在使用的 checkout。共享 CUTLASS 依赖只读、固定版本，每批保留实际使用的源码/依赖身份。
- **共享存储不足时使用节点临时盘。** 在已取得的 Slurm 分配内核对 /tmp 的文件系统与余量，再流式传入本批源码；编译和采样在计算节点完成，结束时直接回传本地 results。临时盘路径写入作业记录，不当作长期归档。job 738097 已验证这条路径，无需向超配额的 home/scratch 写入。
- **回传可独立检查的完成批次。** 沿用原 runner 的 source、build、environment、cases、samples 与哈希；先传到本地新的接收目录，核对清单和哈希，再标为可分析。源码、SASS、正确性与失败记录一起传，不只传漂亮的表格。
- **控制的是总存储量。** 管理者把三个待运行批次的预计体积相加，对比用户及项目配额与本地余量。目录名不同不会获得独立 quota；遇到不足先缩小采样批次或准备归档容量，不靠自动重试继续写。旧数据不删，本轮临时副本如需清理，由管理者在确认本地完整副本后单独列明并执行已获授权的清理。
- **同步现有证据，不建设新交付系统。** 沿用现有运行元数据；不增加 delivery-coverage、验收目录或第二套任务数据库。下面的管理表加每组交回消息即可。

每组在“离线完成”“代码可采样”“GPU 批次完成”“发现影响别组的变化”四个节点交回一次；长采样期间只报告 job 状态、已完成条件数和实际问题，不按分钟重复发消息。

交回格式：

~~~text
组别 / 原实验：
基点 SHA → 本组提交 SHA：
改变的文件及共享文件需求：
运行位置：job ID、节点、GPU UUID、源码/二进制身份
结果目录 / 可复核命令：
结论：可进入模型的关系、仅诊断的结果、失败或不可辨识部分
受影响的其他组 / 下一步最小工作：
~~~

启动时用户应明确授权管理与执行对话之间的任务消息和结果回报；[第 7 节](#goals)的启动文本已包含这一点。目标模式之间没有自动共享上下文，消息中给出提交 SHA、路径与事件定义，不让接收方凭一句“已完成”猜测状态。若暂时没有跨对话消息工具，用户转贴上述短回报，Git 与归档仍是实际证据。

## 4. ROMEO 多 GPU 并行方式

这里的“GPU 实例”是 **Slurm 分配中的 GPU 作业**。截至 2026-10-09 查阅的[ROMEO GPU 文档](https://romeo.univ-reims.fr/documentation/ressources/romeo_2025/utiliser_des_gpu/)写明每个 ARM 计算节点有四张 GH200。armgpu 是 constraint，不是 partition；该用法见[现有 launch_romeo.sh](../../../../../../microbench/gh200_resource_campaign/launch_romeo.sh)和[ROMEO 作业参数表](https://romeo.univ-reims.fr/documentation/ressources/romeo_2025/lancer_un_calcul/)，不由 GPU 页面单独推导。使用 sbatch 或分配内的 srun，保留 Slurm 设备绑定，不能通过直接 SSH 节点看到其他 GPU 后自行占用。

**首选：最多三个独立节点上的作业并行，每节点一个正式计时流。** A/B/C 各自负责一个准备好的批次，批次内部串行跑 baseline/variant、plain/trace 和计数器。这样保留各组完整的成对条件，又不要求所有实验共享一张卡排队。

整节点独占有资源代价：[Slurm 对 --exclusive 的说明](https://slurm.schedmd.com/sbatch.html#OPT_exclusive)是分配节点的全部 CPU/GRES，而不只是命令表面请求的一个 GPU。三个独占节点可能占用十二张 GPU 的调度额度，虽然只启动三个计时流；实际以 scontrol/sacct 的 AllocTRES 为准。不得把“最多三个计时流”宣传成“最多占用三张卡”。

若节点或额度不足：

- 有两个独立节点就两组采样、另一组继续 CPU 分析；只有一个则按“供给→输出/边界→时间”依赖安排批次，模型进入冻结前必须补齐该轮实际使用的校准。
- 同一独占节点上的不同 GPU 可以先并行编译或做正确性检查。若要并行正式计时，先比较相同基线的单独运行与多卡并行，核对 CPU/NUMA 绑定、模组功耗、频率和时间偏移；没有该对照，不默认互不干扰。频率/主机间隙研究和 V09 优先采用单计时流。
- 不为排队中的同一批次重复提交多个副本，不占着空闲 GPU 等本地开发，不取消其他研究的作业。

**本轮已查询账户与存储：** r260073 关联可见，查询时无本账户运行作业；并发上限的空字段不解释为无限。home、scratch 均已接近 20 GB 硬上限，项目组约 18.83 GB 且超过软限，本轮不向这些目录追加。三个并发作业仍取决于实际分配。每次新增大批次再核对余量，不把它变成每个 case 的重复准备流程：

~~~bash
squeue --me
sinfo -N -o "%N %f %G %t"
sacctmgr show Association where user="$USER"
sacctmgr show qos
scontrol show partition short
mmlsquota --block-size auto gpfs
mmlsquota --block-size auto -g r260073 gpfs
~~~

r260073 沿用本项目现有运行记录，启动时确认当前账户关联仍有效；QOS 查询不可用时依据可见的 association/作业限制，不能将未知额度写成无限。ROMEO 的[作业文档](https://romeo.univ-reims.fr/documentation/ressources/romeo_2025/lancer_un_calcul/)与[存储文档](https://romeo.univ-reims.fr/documentation/ressources/romeo_2025/espaces_de_stockage/)分别说明调度和配额查询；公开默认值不替代用户实际限制。

提交方式示例：三个组先各自准备一个只调用原实验入口的 batch 脚本。下列 supply.sbatch、output-boundary.sbatch、clock-input.sbatch 是待准备的本批脚本名，不是仓库中已存在的新运行器。

~~~bash
gh200_submit_args=(
  --account=r260073 --constraint=armgpu --partition=short
  --nodes=1 --ntasks=1 --cpus-per-task=4 --mem=32G
  --gpus-per-node=1 --exclusive --time=02:00:00
)
sbatch --parsable "${gh200_submit_args[@]}" --job-name=gh-supply supply.sbatch
sbatch --parsable "${gh200_submit_args[@]}" --job-name=gh-output output-boundary.sbatch
sbatch --parsable "${gh200_submit_args[@]}" --job-name=gh-clock clock-input.sbatch
~~~

两小时只是单个 batch 的示例 walltime，应按 pilot 耗时、剩余条件数和余量调整，不是整个研究的人工截止。三次提交是否能同时 Running，由 Slurm 和实际额度决定。管理者一次分配本轮提交名额，每组只提交自己的一个批次并立即回报 job ID，避免管理者与执行组重复提交。正式命令还应设置本批独立工作目录与日志路径。

每个 batch 在计算节点加载 romeo_load_armgpu_env 和本组核对过的 CUDA 12.9；现有脚本使用 spack load cuda@12.9.0，仍以 nvcc 实际版本为准，不静默改工具链。普通探索批次通过单任务、单 GPU 的 srun step 执行原有 build/check/sample 命令，记录实际 UUID。需要指定参考 UUID 时使用下一节的绑定方式；不能在只获配另一张 GPU 的 step 中覆盖 CUDA_VISIBLE_DEVICES 试图访问它。首次数值与资源检查先于正式计时，不能在登录节点运行 GPU 探针。

## 5. 参考卡、自动冻结与 V09 人工确认

并行探索卡 G_A/G_B/G_C 仍按实际分配登记，相对对照必须各自在本卡完成。各组交回源码、事件关系、参数形式与同卡证据，不能从另一张卡借一个时间作为同期基线。
