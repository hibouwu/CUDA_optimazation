# R08：波次/尾部与 tile 遍历（L2 复用）

[总计划](README.md)。2026-10-07，Slurm 735668，romeo-a050，GPU-3953fe72…（GH200 120GB，驱动 590.48.01），GPU 功率上限 900 W，Module Power Limit 680 W（默认 1000 W）。CUDA 12.9.41 / sm_90a，CUTLASS v3.9.2。与 R00、R07 不是同一块卡；同节点另一块 GPU 上有其他作业在运行。

## 问题

1. K=4096 时，单调用时间怎样随输出 tile 数相对 132 个 SM（66 个 cluster 对）变化？离散波次 `a + ⌈U/132⌉·t` 与按分数负载 `a + (U/132)·t` 哪个更符合？
2. M=N=8192、K=4096（约 15.5 波）时，持久调度器的 raster 方向、swizzle 与 cluster 2×1/1×1 改变多少吞吐？由此推出的每 SM 输入速率落在 R05-D 的 15–55 B/cycle 之间的什么位置？

## 配置

- CUTLASS 与 [R07](R07-anchor-clock-fixedcost.md) NDEBUG 版相同：FP16→FP32，tile 128×256×64，4 stage，TMA warp-specialized cooperative，`ElementC=void`，epilogue 128×32，持久 tile 调度器。cluster 2×1×1 为默认；1×1×1 用同一源码另编译一份（`-DR08_CLUSTER_M=1`）。
- 调度参数经 `Arguments::scheduler` 传入：`raster_order`（Heuristic / AlongM / AlongN）与 `max_swizzle_size`（1/2/4/8）。问题 1 用默认值（Heuristic、swizzle 1）。Heuristic 在 tiles_n > tiles_m 时取 AlongM，否则 AlongN。
- 调度单位 U = `blocks_per_problem`：tiles_m 先向上取整到 cluster M 的倍数（2×1 时为偶数），swizzle>1 时再取整到 swizzle×cluster 的倍数。补出的 tile 照常被调度（越界部分由 TMA 填零、不写回）。
- grid：2×1 时 [2,66,1]（AlongN）或 [132,1,1]（AlongM），U<132 时截到 U。`cudaOccupancyMaxActiveClusters` 报 66（2×1）/132（1×1），全部 CTA 同时驻留。
- 构建：ptxas 日志无 C7510；GEMM kernel 与时间戳包装 kernel 均为 8 条 HGMMA、2 条 `WARPGROUP.DEPBAR`。
- 正确性：393 个进程（含 16 个 pilot）均做 R00 抽样 FP64 检查（256 点，含 tile 边界行列），误差全为 0。

## 计时边界

| 名称 | 窗口 | 说明 |
|---|---|---|
| call | 2 次模块加载调用 → 空闲 0.5 s → 5 次 event 包围的单调用，每次后接 20 µs clock 探针；取 5 次中位数 | 含主机提交；主指标 |
| graph | 一个 graph 内 10 次连续调用，总时间/10（仅问题 1） | 不含逐次主机提交，但连续负载使频率下降 |
| 调用后探针 | 每次 call 之后 20 µs 的 clock64/globaltimer，132 个 block 中位数 | 调用**之后**的频率，不是调用内平均频率 |
| 每 CTA 时间戳 | 包装 `__global__` 直接调用 `Kernel::operator()`：thread 0 入口记 globaltimer 与 `%smid`；返回后每个 warp 的 lane 0 对出口时间做 atomicMax | 每次启动前空闲 0.3 s；每 CTA 的 tile 数按调度器线性序号 `q, q+132, …` 计算 |

每点 10 个独立进程（时间戳 3 个进程 × 3 次启动），每轮随机打乱顺序。CV 为进程间中位数的变异系数。

8192² 时 tiles_m=64 > tiles_n=32，Heuristic 等同 AlongN，未单独测。cycle/Ktile = (call − a)/(16×64) × 调用后 GHz，a=0.03 µs 取自问题 1 离散拟合。逻辑输入按每 tile 每 Ktile 49152 B（A 16 KiB + B 32 KiB）；L2 请求量按 2×1 cluster 内 B 多播，每 SM 32768 B 计。

**手算**

- 波次：528 tile 的 call 中位数 190.13 µs；离散模型 0.03 + 47.09×⌈528/132⌉ = 188.40 µs，残差 +1.73 µs；分数模型 30.34 + 40.80×4.0 = 193.5 µs。
- 遍历：2×1、AlongN、swizzle 8，806.9 µs。2×8192²×4096 = 549 755 813 888 FLOP，除以 806.9 µs 得 681.3 TFLOP/s。关键 CTA (806.9−0.03)/(16×64) = 0.7880 µs/Ktile，乘 1.671 GHz 得 1316.7 cycle/Ktile；49152/1316.7 = 37.3 B/cycle/SM，按多播后的 L2 请求量为 32768/1316.7 = 24.9 B/cycle/SM。

## 结论

- **离散波次模型成立**：K=4096、单调用时 \(T \approx 47.1\cdot\lceil U/132 \rceil\ \mu s\)（截距约 0），RMS 残差 2.0 µs；分数负载模型 RMS 16 µs。时间戳给出直接证据：每个 tile 约 43 µs，与同时活动的 SM 数无关——136 tile 时第二轮只有 4 个 CTA，它们的第二个 tile 仍用 85.98−42.82 = 43.2 µs；266 tile 时 2 个 CTA 的第三个 tile 使总时间从约 90 µs 增到 135 µs。
- 同一轮内 tile 数从 64 增到 132，call 只增 46.0→48.9 µs（约 6%）；离散+分数拟合的分数项为 2.1 µs/波。半满的波与满波几乎同价，U 刚超过 132 的整数倍时时间跳一整轮。
- **边界与补齐**：U 是 cluster 补齐后的 tile 数。M=N=2000 与 2048 同为 128 个 tile，时间相同（48.45 vs 48.59 µs），越界 tile 不省时间；3000²（288）、4000²（512）分别落在 3、4 轮台阶上。tiles_m 为奇数时 2×1 cluster 补出一列 tile：265 个 tile 补成 318，与 396 个 tile 同为 3 轮。
- 形状影响每轮时间：134 个 tile 的 256×17152 比 136 个 tile 的 1024×4352 慢 8%（98.8 vs 91.4 µs，同为 2 轮、AlongM）。推断：M=256 时每个 B 面板只被一个 cluster 对使用，B 的 L2 复用接近 R05-D 的“独立大源”情形；本组未隔离原因。
- graph（10 次连续调用）在 U 为整波倍数附近的大形状（264、396、512、528）上比单调用慢 8–9%，调用后探针约 1.58–1.60 GHz（单调用 1.69–1.78）；持续负载下的降频使连续调用不能直接套用单调用的每轮时间。
- **遍历与 cluster**：TFLOP/s 在 619–681 之间。swizzle 8 比 swizzle 1 快 6.2–7.6%；2×1 比 1×1 快 0.8–5.0%（最大为 AlongN、swizzle 4）；raster 方向差 ≤1%，只有 1×1、swizzle 4 时 AlongM 快 3.0%。换算成关键 CTA 的 cycle/Ktile，16 个配置都在 1315–1349 之间（±1.3%），而时间差 10%。时间差几乎全部与调用后探针频率（1.525–1.671 GHz）同向变化。
- 推断：在本组配置下，遍历方式与多播通过频率影响速度——更好的 L2 复用减少片外流量与功耗，在 680 W 模块功率上限下换来更高的 SM 频率——而不是改变每 cycle 的主循环进度。证据限于调用后探针，调用内平均频率与 DRAM 流量都未直接测。
- **隐含供给**：所有配置下关键 CTA 消耗的逻辑输入为 36.4–37.4 B/cycle/SM（多播后 L2 请求 24.3–24.9，1×1 为 36.9–37.4），位于 R05-D 的 15（无复用）与 55（共享小源）之间，低于满速 WGMMA 所需的约 48。这是供给的下界：1×1 的 L2 请求量是 2×1 的 1.5 倍、各 swizzle 的复用差别很大，cycle/Ktile 却不变，所以推断这个速率不由 L2 供给决定，约 1320 cycle/Ktile 中超出 1024 的部分来自其他环节（epilogue、每 tile 的流水建立等，未拆分）。
- 模型接入：整卡时间按 \(\lceil U/132 \rceil\) 轮计，U 用 cluster 与 swizzle 补齐后的 tile 数。K=4096、单调用协议下每轮约 47 µs；CTA 内每 tile 时间从 1 轮的 42.7 µs 增到 4 轮的 46.4 µs（185.4/4，调用后频率同时下降），单调用比末 CTA 出口多 2.5–5 µs。频率按负载协议给定，不能用单一常数。

## 未解决

- 调用内平均频率未测（探针在调用之后）；问题 2 的 cycle 换算与“频率解释”依赖这一点。
- 256×17152 的 8% 差别未分离出 L2 复用与 raster 的贡献。
- 时间戳只给 CTA 入口/出口，没有每个 tile 的 mainloop/epilogue 分段（需要修改持久循环，本组未做）。
- 每 tile 约 1320 cycle/Ktile 中超出 1024 的约 22% 尚未拆分。

## 后续修正（R09）

本页的 cycle/Ktile 和"频率解释"都用调用**后**探针频率（1.525–1.671 GHz）换算。[R09](R09-inkernel-clock-stages.md) 在调用内部测得 8192³ 的平均频率只有约 1.38–1.41 GHz，调用后探针明显偏高。因此 1315–1349 cycle/Ktile 偏大；R09 在 2048² 上直接测得主循环为 1024 cycle/Ktile 加常数，超出部分是每 tile 的预填、epilogue 等固定段摊到 K 上。"遍历方式通过频率影响速度"的推断仍需用调用内频率重新核对。
