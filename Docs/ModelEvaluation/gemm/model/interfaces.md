# 操作、资源与事件接口

[建模入口](../README.md) · [FP32 分块 GEMM 示例](../schemes/fp32_simt_tiled.md)

本文件规定 L0–L4 和方案模型共用的接口。问题参数仍由 [problem.md](../problem.md) 定义；各架构维护服务参数与物理限制，方案模型负责将配置展开为操作、依赖和存储生存期。

## 1. 模型输入与输出

\[
\Phi(w,x)=(\mathcal O,\mathcal E,\mathcal D,\mathcal A),\qquad
\widehat T=\operatorname{Eval}(\Phi(w,x),h,s;\theta).
\]

| 对象 | 内容 |
|---|---|
| \(w\) | 问题实例：尺寸、精度约束、布局、输出要求及计时边界 |
| \(x\) | 执行组织：分块、线程映射、搬运路径、缓冲、任务顺序；由方案定义可选域 |
| \(h\) | 硬件资源、作用范围、容量、指令支持和服务限制 |
| \(s\) | 初始缓存、已有缓冲状态、可用 SM、频率及外部竞争等运行条件 |
| \(\theta\) | 指定条件下的延迟、启动间隔和服务率；未知值可保留为符号 |
| \(\mathcal O,\mathcal E\) | 操作集合及带事件类型的依赖边 |
| \(\mathcal D\) | 每个操作对各资源的需求；有效 FLOP、执行指令和访存事务分别计量 |
| \(\mathcal A\) | 分配对象、实际分配量及占用区间 |

`Eval` 必须同时给定依赖、资源仲裁和服务规则。仅有一个依赖 DAG，或各资源独立峰值，还不足以确定完成时间。无法确定的服务参数应作为结果条件或缺失项输出，不自动填零或换用另一精度的数据。

## 2. 基础操作

L0 的基本构件称为“操作原语”，包括计算、搬运、同步和辅助操作。它不是 `atomicAdd` 意义上的原子性，也不预设为一条 SASS 指令。[CUTLASS Atom 定义](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/gemm_api_3x.html#atom-api) 可用于对照线程与数据参与范围。

| 字段 | 必须说明的内容 |
|---|---|
| 操作与形状 | 类型、精度、指令/请求形状、重复次数；计数是线程操作、warp 指令还是搬运请求 |
| 路径与参与者 | 输入/输出位置、访问宽度、布局与对齐，以及 thread/warp/CTA/cluster 范围 |
| 前置条件 | 哪个输入就绪、哪个资源可用、哪个同步状态成立后才能发出 |
| 资源需求 | 关联资源 ID、需求量、单位及读写方向；逻辑字节与服务事务分别记录 |
| 服务条件 | 依赖或独立流、缓存状态、在途请求、并发配置与时钟口径 |
| 完成接口 | 发出、执行完成、指定消费者可见、源/目标缓冲可复用等事件 |
| 参数依据 | 规格、条件上限、经验服务、教学假设或待确定；经验参数保留适用域 |

一个搬运操作可以使用多条通路，但不拥有额外的一份带宽。同步原语描述状态与发射/通知成本；等待其他操作到达所需的时间由事件关系产生。

## 3. 共享资源

物理资源只有一份定义。操作从哪一层被引用，不改变它的共享范围。以下 ID 作为模型命名约定，资源参数引用 `hardware/<设备>/` 中的对应文件；文件所在层级不构成额外的执行依赖。

| 资源 ID | 作用范围 | 参数位置与用途 |
|---|---|---|
| `sm.compute.fp32` 等 | 指定 SM 及执行路径 | `hardware/<设备>/L0.md`：计算服务及条件；不同精度是否共享执行能力须另有依据 |
| `sm.issue` | 指定 SM；必要时细分调度分区 | `hardware/<设备>/L1.md`：多个操作流的发射约束 |
| `sm.storage.reg`、`sm.storage.smem` | 指定 SM；按实际粒度分配 | `hardware/<设备>/L1.md`：容量、分配与驻留；Thor 的 TMEM 按其自身规则另列 |
| `sm.access.*` | 指定片上路径 | `hardware/<设备>/L1.md`：线程 SMEM、MMA 取数、TMEM 访问等条件化服务；未知共享关系不能推定为独立 |
| `gpu.cache.l2` | GPU 共享 | `hardware/<设备>/L2.md`：缓存容量、服务与状态；L3/L4 聚合使用需求 |
| `gpu.memory.external` | GPU 或平台共享，以实际硬件为准 | `hardware/<设备>/L2.md`：外存容量、读写联合服务；Thor 与 GH200 分别描述 |

分配量与有效数据大小分别定义；数据不再使用、缓冲可以复用和硬件分配可以释放也不是同一个事件。存储对象的占用区间为 \([a_j,u_j)\)，实际分配量为 \(v_{j,r}\)：

\[
\sum_{j:\,a_j\le t<u_j}v_{j,r}\le C_r.
\]

若采用可同时兑现的服务份额 \(b_{j,r}(t)\)，还需满足：

\[
\sum_j b_{j,r}(t)\le\mu_r(t).
\]

这里 \(b\) 与 \(\mu\) 必须使用同一需求单位和时间口径。独立测得的读、写峰值不能直接视为可同时兑现的份额；方向、事务形状或并发改变时，服务模型也可能改变。

## 4. 事件与组合

| 事件 | 含义 |
|---|---|
| `eligible` | 该操作所需输入、同步状态和逻辑依赖已满足 |
| `issue` | 发射资源和在途容量允许请求进入执行路径 |
| `complete` | 约定范围内的操作执行完成 |
| `visible(consumer)` | 按所选同步与内存语义，指定消费者可以使用结果 |
| `release(object)` | 最后需要该对象的操作已满足释放条件，可以复用存储 |

这些事件不能默认合并。异步搬运的发出不等于数据可用；源缓冲可复用与目标结果可用也可能不同。`cp.async` 的等待与可见性以 [PTX 完成语义](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cp-async-wait-group-cp-async-wait-all) 为准，不能用一个 barrier 代替所有异步路径的完成条件。

对前置事件集合 \(\mathcal P_i\)，先确定操作的逻辑就绪时刻：

\[
a_i=\max_{e\in\mathcal P_i}t_e.
\]

仅在**固定服务条件、同类操作、规定发射顺序**下，可用如下简单流水线服务器：

\[
t_i^{\mathrm{issue}}=
\max(a_i,t_{i-1}^{\mathrm{issue}}+II,u_i^{\mathrm{slot}}),\qquad
t_i^{\mathrm{complete}}=t_i^{\mathrm{issue}}+\ell.
\]

\(II\) 是允许的启动间隔，\(\ell\) 是该条件下的完成延迟，\(u_i^{\mathrm{slot}}\) 是一个在途槽可用时刻。第一个操作没有前驱发射约束。若操作必须完成后才能服务下一个，应使用非重叠服务规则；不同操作共用执行单元时，需统一仲裁，不能各自独立运行这条递推后再取最大值。

例如，barrier 的释放事件需要参与者到达及其要求的异步完成条件全部满足；参与者到达时间本身由前面的操作推导。指令执行成本与等待时间分别记录。

## 5. 计时与层间边界

同一路径必须选择一种计账方式：

- **整段服务**：用从约定请求入口到结果可用的条件化服务描述一段操作；内部取数、排队或同步若已包含，就不再加一次。
- **分段服务**：显式展开请求通过各资源及同步条件的事件，以这些事件推导完成时间；整段实测仅用于对照或校准。

两者可以用于不同对象，但一个对象不能同时按两种方式收取同一段成本。物理共享容量仍需统一约束；采用含竞争的整段服务时，不额外叠加同一竞争的排队时间。

| 层级 | 组合职责 |
|---|---|
| L0 | 定义基础操作及其条件化服务 |
| L1 | 将操作映射到工作块内线程和片上数据；推导片上执行、分配与驻留约束 |
| L2 | 按供给、缓冲和阶段状态组织协作流水线；可直接引用 L0 的搬运原语 |
| L3 | 安排所有工作 tile，统一处理共享服务与阶段衔接，求完整 kernel/GEMM 完成时间 |
| L4 | 根据算子依赖与中间结果接口组合执行；按实际融合边界复用下层模型 |

L1 中给定的一串片上工作块不隐含 GMEM 预取、环形缓冲或完整 K 主循环；这些执行顺序在 L2 的方案实例中给定。各层输出可组合的需求和事件，不要求每个操作都依次经过所有层。

最终从计时起点到所有必要输出可用的最晚时刻得到 \(\widehat T\)，再按 `problem.md` 的有效工作量计算 FLOP/s 和参考周期性能。资源上限给出的时间下界、带条件的时间预测与实测值分别报告。

## 6. 时间下界与条件化预测

对计时边界内必须完成的资源需求 \(D_r\)，若 \(\mu_r\) 是同范围、同单位下有效的服务率上限，则：

\[
T\ge\max\left(T_{\mathrm{dep,LB}},\ \max_r\frac{D_r}{\mu_r}\right).
\]

\(T_{\mathrm{dep,LB}}\) 为必需依赖路径的延迟下界。需求可以是字节、指令或计算量，分别与对应服务率配对。该式给出时间下界；完整时间还受启动、等待、有限并发与排空影响。使用经验速率得到的是条件化估计，不能自动称为严格下界。

[Roofline 作者介绍](https://amcr.lbl.gov/wp-content/uploads/2025/11/roofline-intro.pdf) 可用于建立计算与数据搬运的吞吐限制；[ECM 原论文](https://arxiv.org/html/1410.5010v2) 提醒模型必须明确可重叠和不可重叠的成本。借鉴这些方法时，具体 CPU 重叠规则不直接用作 GPU 的规则。
