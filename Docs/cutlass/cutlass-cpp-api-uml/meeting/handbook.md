# CUTLASS 实现接口对齐会：现场审阅手册

这份手册用于第一次看到同事接口方案时组织讨论。会前不需要拿到完整代码；会上先明确实现承诺，再沿一次实际支持的 GEMM 检查接口之间是否能接得起来。遇到只有口头说明、尚无实现或实验结果的部分，记录为待核验，不把它当成已经证明正确。

CUTLASS 在这里提供职责划分和具体接口的参照。评审对象不必复制它的类名、层数或硬件指令：只要兼容范围允许，职责可以合并，也可以重新划分。需要追究的是交接条件有没有遗漏，以及使用者是否能够据此正确调用。

官方参照固定在提交 `8f50b052e1099fb982392a622caab69b97b63128`，库版本为 4.6.0，以其中的 3.x API 体系为阅读主线。现有图集只对已列明的路径提供详细证据，不代表全库接口已经审查完毕。

## 1. 开场先确认：今天到底对齐什么

请同事先说明下面四件事，再展示类图。否则双方很容易一边讨论名字，一边默认了不同的实现目标。

- **兼容程度。** 是已有 CUTLASS 调用代码不改就能编译，允许改一层适配，还是只要求提供相同计算能力？源代码兼容还要问版本、头文件入口以及支持哪些模板实例。
- **实现边界。** 方案包含哪些部分：问题描述、类型选择、设备启动、数据搬运、矩阵计算、结果处理、工作分配？哪些由调用方、运行时或其他库承担？
- **目标硬件。** 是已有 NVIDIA GPU，还是另一种硬件？后一种情况需要解释等价的执行和同步条件，不要求使用 TMA、TMEM 或 warpgroup 等名称。
- **当前承诺。** 哪条路径已经实现，哪条只设计了接口，哪些明确不支持？今天以一条已经支持的路径展开，其余承诺分别记录。

如果对方声称“兼容 CUTLASS”，请把这句话改写成可检查的范围，例如支持的入口、数据类型、布局、形状限制、架构和错误处理方式。未支持某个场景本身不构成错误；承诺支持却不能表达必要参数，才是需要解决的问题。

## 2. 先走通一次 GEMM，再回到接口划分

请同事选择一个实际支持的 GEMM，给出计算式、矩阵形状、数据类型、布局以及运行配置。普通矩阵乘可以按 `D = αAB + βC` 说明；如果当前接口不支持其中某一项，应直接注明，而不是用一个不相符的例子开场。

沿同一份输入依次问下面六步。每一步都要指出负责的接口、接收的对象、输出或修改的对象，以及进入下一步的条件。

1. **调用方准备什么。** A、B、C、D 的指针、大小和布局由谁提供？配置在编译期选定，还是每次调用传入？
2. **什么情况下允许执行。** 哪个接口检查类型、形状、对齐和硬件限制？它的检查能覆盖什么，哪些条件仍由调用方保证？
3. **执行前形成什么状态。** 需要多少临时空间，由谁分配和初始化？面向用户的参数怎样转成设备执行所需的参数？
4. **设备如何得到工作。** 谁提交任务，谁取得一个工作块，搬运和计算分别由谁发起？各部分怎样知道彼此已完成所需的前置工作？
5. **结果何时可读。** 哪个事件表示计算或写回完成？调用返回是否只表示提交成功？调用方应通过什么等待或依赖保证读取安全？
6. **何时能够复用和释放。** 临时缓冲、描述符、同步对象和输出空间各自要等到什么条件成立，才能被改写或释放？

第一次只走一条完整路径。遇到分支先记下入口和条件，走完后再展开；不在每个类名出现时转去解释整个类。这样可以判断接口划分是否服务于实际执行，而不只是看起来分层整齐。

官方查阅入口：[Host 调用过程](references.md#ref-host)、[编译期选择](references.md#ref-build)、[参数和职责交接](references.md#ref-handoff)、[同步与资源使用](references.md#ref-sync)。

## 3. 现场必问的 12 个问题

以下问题按一次执行的顺序排列。回答中出现“自动处理”“底层保证”或“和 CUTLASS 一样”时，继续问到负责的对象、调用位置和生效条件。暂时没有源码也可以完成设计讨论，但证据状态应如实保留。

### 3.1 一个用户请求，究竟由哪些接口共同表达

**问：** 请用这次 GEMM 的实际配置说明，哪些选择写进模板或构建配置，哪些参数在每次运行时传入？

追问类型、布局、Tile、执行策略和问题大小分别在哪里确定。如果用户改变一个参数，需要重新编译、重新初始化，还是可以直接再次执行？若存在自动选择，问清选择输入、结果类型或实现，以及不满足选择条件时的行为。

希望看到一个可编译的使用片段，以及对应的参数定义或构建选择。不能仅凭同名 `Auto` 认定选择行为相同。参照：[编译期选择](references.md#ref-build)。

### 3.2 各层之间交接的对象是什么

**问：** 用户传入的参数经过哪些转换，最终设备入口收到什么？

追问每次转换是否复制数据、计算派生值、保存指针或生成描述符；这些对象依赖哪些外部内存，其生命周期到何时。若两个组件都声称负责同一件事，明确谁作最终决定；若谁都不负责，明确缺失的职责。

希望看到参数类型、转换接口，以及调用前后的同一组字段。返回类型相同不足以证明其内容和生命周期相同。参照：[参数和职责交接](references.md#ref-handoff)。

### 3.3 数据表示能否唯一确定实际访问的元素

**问：** 给定一个逻辑元素坐标，接口提供的信息能否确定它在内存中的位置和表示？

追问行列语义、stride 单位、批次维度、对齐要求和边界处理。对打包数据，要区分逻辑元素数、存储字节数和指针对齐；对布局转换，问清转换前后的对象由谁持有。不要只问“支不支持 RowMajor”。

希望看到一组非方阵、非默认 stride 的具体地址对应关系，或覆盖这些条件的测试。若只支持连续布局，应把限制写入接口说明和检查条件。参照：[参数和职责交接](references.md#ref-handoff)。

### 3.4 不合法的请求在哪里被拒绝

**问：** 用户传入一个当前实现不支持的形状、类型、对齐或硬件配置时，谁负责阻止执行？

追问是在编译期报错、显式检查失败、初始化失败，还是启动后才报错。检查是否由后续接口自动调用，必须以调用关系为准；不能假定存在检查函数就一定执行了检查。

希望看到至少一个被拒绝的输入及对应结果，并区分调用方前提、运行时检查与设备错误。参照：[Host 调用过程](references.md#ref-host)。

### 3.5 临时空间和可复用状态由谁管理

**问：** 执行需要哪些临时空间或持久状态，大小怎样取得，谁负责分配、初始化和释放？

追问同一对象能否换指针、换问题大小、重复运行或并发使用。更新参数之后，哪些状态仍有效，哪些必须重建？若提供 `update` 与 `initialize` 两类入口，请分别解释，不能从名字推断二者等价。

希望看到资源所有者、有效期和更新前提，以及一例复用操作的调用顺序。参照：[Host 调用过程](references.md#ref-host)。

### 3.6 启动成功和结果完成怎样区分

**问：** 执行接口返回成功时，设备究竟完成到了哪一步，调用方此时能否读取或释放相关内存？

追问提交接口、设备入口和完成通知的关系；异步执行使用哪个 stream、队列或事件，后续任务怎样建立依赖。如果接口本身不等待，应明确谁等待，以及等待能观察到哪些结果。

希望看到调用方实际使用的完成机制和错误检查位置。成功提交、设备执行成功与数值正确需要分别记录。参照：[Host 调用过程](references.md#ref-host)。

### 3.7 搬运和计算为什么不会访问尚未准备好的数据

**问：** 请沿一块输入缓冲说明：谁发起写入，谁确认完成，谁等待，谁随后读取？

追问发起者和参与者是否相同，通知覆盖哪些线程或计算单元，完成条件按事务、字节数还是其他单位定义。硬件自动完成一部分工作时，仍要指出软件必须提供的初始化和计数条件。

希望看到具体生产者、消费者、等待位置和缓冲对象的对应关系；有硬件约束时给出指令或硬件接口依据。参照：[同步与资源使用](references.md#ref-sync)。

### 3.8 下一轮何时可以覆盖缓冲或复用同步对象

**问：** 同一缓冲进入下一轮之前，怎样确认上一轮所有需要的读取已经结束？

追问多级缓冲的 stage、循环轮次或 phase 怎样推进；哪个事件允许源缓冲复用，哪个事件才表示目标写入完成。两个事件可能不同。异常退出和最后一轮是否仍会完成必要的等待与释放？

希望看到一次跨轮次的顺序或状态说明，尤其是最后一轮和复用边界。只有正常路径的 API 名称列表不足以回答。参照：[同步与资源使用](references.md#ref-sync)。

### 3.9 工作归属怎样确定，如何避免遗漏和重复

**问：** 一个输出区域由谁计算，工作索引怎样映射到问题、输出坐标和归约范围？

追问边界 Tile、无工作参与者和最后一个任务的行为。若同一输出由多个参与者共同归约，谁决定归约顺序、临时结果位置和最终写回权？静态映射和动态取任务都可以，但必须能解释唯一归属或受控协作。

希望看到当前调度方式下一组可核对的映射，以及边界或不均衡工作量的结果。参照：[参数和职责交接](references.md#ref-handoff)。

### 3.10 累加结果如何交给后处理并写回

**问：** 计算结束后，累加结果以什么类型、布局和存储形式交给后处理，后者何时能够读取？

追问精度转换、`α`、`β`、C 的读取和 D 的写回由谁负责，以及 C 与 D 是否允许相同或重叠。若融合其他运算，明确其计算顺序、广播方式和需要的额外参数。

希望看到这一交接的类型和操作顺序，并有与声明精度相符的参考计算。不能仅凭“输出是 FP32”推断中间累加和转换精度。参照：[参数和职责交接](references.md#ref-handoff)。

### 3.11 超出基本 GEMM 的承诺在哪里体现

**问：** 当前还承诺支持哪些问题，它们比刚才那条路径多出的信息和职责在哪里表达？

只追问对方承诺的场景。Grouped GEMM 问每个问题的形状、指针和工作归属；MoE 问路由与 token 排列由谁完成、专家 GEMM 接收什么；Block-Scaled 问数值与 scale 的粒度、格式和坐标对应；Attention 问计算范围、mask、归一化以及中间结果管理。

希望看到扩展参数如何进入同一条完整路径。若能力暂未支持，记录范围即可；若只实现其中一个子步骤，不把它记成整个场景已完成。参照：[参数和职责交接](references.md#ref-handoff)。

### 3.12 目前的证据究竟证明了什么

**问：** 请把当前结果分别归到接口设计、源码对应、编译结果、运行正确性和性能，而不是只给一个“通过”。

追问证据的版本、配置、输入和环境。一次编译能说明选中的类型或生成代码，不能说明设备已经运行；一次正确运行也不能替代全部支持范围的检查。性能需要独立说明比较基准和测量条件。

希望看到能够定位或重现的材料；未带到现场的材料，记录补交内容与负责人。对于关键同步约束，源码依据和实际运行观察都应注明各自能够支持的结论。

## 4. 怎样判断差异是否需要修改

先把差异还原成可观察的行为，再讨论接口形式。下面四类结果应分开记录。

- **解释已经清楚。** 对方说明了职责、参数和使用条件，当前没有明显矛盾，但尚无足够材料确认实现符合说明。
- **已有证据支持。** 指定源码、编译或运行证据支持某个明确结论；结论只覆盖该证据对应的版本、配置和范围。
- **有意的设计差异。** 与 CUTLASS 不同，但符合事先约定的兼容范围，额外限制和调用方责任也已说明。记录取舍，不因不同而要求改回去。
- **需要补充或验证。** 有未定义的条件、互相矛盾的说明、缺少的实现或未覆盖的测试。记录具体问题，不用笼统的“待优化”代替。

这些状态可以同时存在。例如一个与官方不同的调度方案，设计理由已经解释清楚，但其并发正确性仍待验证。不要用单一“通过”抹去这个区别。

出现下列情况时，通常需要落实修改或补充验证：没有对象负责必要的参数转换；调用方无法知道何时安全读取和释放；同一缓冲的覆盖条件与读取条件冲突；承诺的布局无法由参数唯一表达；不支持的输入没有可辨认的拒绝方式。

这些都要落到实际路径和具体接口上。仅仅层数不同、名字不同、没有使用某种 NVIDIA 硬件机制，不能据此判定方案有误。

## 5. 会议结束前留下什么

使用[现场记录模板](review-record-template.md)，至少留下这次讨论的支持范围、走过的 GEMM 配置、接口交接路径，以及每个未关闭问题。

每条问题应能让会后接手的人独立处理：指出当前说法或证据、缺少的条件、需要补交的材料，以及判定完成的方法。负责人和时间由参会者确认，不在会前代填。

如果关键路径尚未讲通，会议结论应是“需要补充设计说明”，而不是“接口总体没有问题”。如果设计已讲通、但只有部分实现证据，可以确认相应设计约定，同时把正确性验证留为独立事项。

资料较多时，优先留下关键路径图和问题编号。详细官方图集用于回答具体疑问，不必在会议上逐页展示；本次现场审查也不等于已经完成全库或全部架构的对齐。
