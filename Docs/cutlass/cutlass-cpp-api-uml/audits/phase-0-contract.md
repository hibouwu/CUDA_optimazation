必须补充的接受条件：

- 分开记录逻辑实体身份、每次声明/定义出现位置和条件实现 variant。每处原始声明可反查实体及归并理由；同一实体的多次声明不能被当作多份独立实现。

## 2. 宏与条件分支：不能仅收录候选就视为生成 API 已覆盖

反例：`include/cute/numeric/integral_constant.hpp:204–248` 通过宏调用生成 5 个一元与 18 个二元运算符接口。仅提取宏定义，或记录“这里有宏生成候选”，均没有得到这 23 个接口。`include/cute/container/tuple.hpp` 同时存在 `#if 0` 旧实现和 RTC/CUDA std 条件分支；单一 host 配置不能代表固定源码的全部条件接口。

README 已要求宏定义/展开来源和未激活分支进入清单，但未明确候选状态与已提取实体状态的区别。

必须补充的接受条件：

- 宏定义、调用位置、展开序号、生成的具体接口与有效条件能双向追溯。未展开、部分展开和解析失败明确是未完成状态，不能以宏候选记录抵充生成 API 完成数。
- 每个预处理区域都有原始条件及处理结果。可达的条件接口须纳入；语法上存在但不可达的内容可作非 API 排除，但须在原始区域清单中保留可核查的排除依据，不能静默丢弃。

## 3. 参数化关系：已有失败隔离，接受证据仍不足

反例：`mma_atom.hpp:104` 的 `mma_unpack` 依赖 `Traits` 等模板绑定；`include/cutlass/pipeline/sm90_pipeline.hpp:442` 调用用户提供的 functor。不能任意选择一个具体叶实现；也不能只记录原始表达式并将所有困难关系标为 `symbolic`。

必须补充的接受条件：

- `symbolic` 的接受材料包含 callee 原始表达式、实参及其绑定表达、可见候选或可核对的 lookup 路径、依赖参数、约束，以及要确定具体目标还缺少哪些绑定。不能在目标参数尚不确定时伪造完整形参映射；此时应记录可确定的部分和精确缺口。
- 用户可提供无限扩展实现的调用，终点明确是已识别的模板/回调接口边界。它不是提取失败，也不是已确定的库内叶实现。
- `configured` 保留具体配置和确认目标的证据，不推广为其他配置下的确定关系。解析错误、不支持的 lookup 和已知应有但未找到的定义分别报告，不借 `symbolic` 合并为可接受终态。
- 将真实提取失败改名为 `symbolic` 的破坏测试必须失败；“参数化”需要正向证据，不能仅凭没有具体目标这一负向事实成立。
