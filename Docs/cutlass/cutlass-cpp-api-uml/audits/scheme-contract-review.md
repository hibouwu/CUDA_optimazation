# 主线方案差异走查

上一目标轮次已实施五步主线，修改了可复核的网页及构建数据，属于有实质推进的检查点。本轮继续从实际方案判断需要出发，没有重新建设快照或恢复细碎实现枚举。

## 为什么需要这次走查

原主线列出了职责和必要条件，但仅靠问题列表，读者仍可能把不同于官方的设计直接当错，或者把同名 API 当成行为一致。本轮补充三类有条件的判定，每类都给出待检验说法、反例、不同前提下的判断，以及下一步需要什么证据。

这些是实现者进行的源码自查和有限测试，不冒称同事已经提出这些方案，也不冒称独立使用审查已经通过。

## 1. 布局表达

反例保留同一问题形状，仅改变A/B的实际行步长。固定源码 `include/cutlass/detail/layout.hpp:57–82` 将 RowMajor 映射到含动态整型分量的步长类型；`include/cutlass/layout/matrix.h:90–110` 也区分实际 stride 与 packed 构造。Host 运行验证了相同RowMajor标签不保证相同地址。

判定不一概要求支持全部布局：明确只支持紧密存储可属于范围取舍；承诺填充而无法表达stride属于信息缺失；有stride却忽略则违反自身接口。具体运行结果及工具链失败历史见[Host布局检查](../verification/scheme-layout/README.md)。

## 2. 完成条件

反例是把 run 的提交成功当作结果已经可以被调用方读取。固定 Adapter 的返回分支检查 `launch_result` 与 `cudaGetLastError`；应用显式等待stream和复制D，TMA源读取完成也是另一层事件。

因此，提供明确完成机制的异步设计可以成立；没有结果交付条件的承诺不能据提交返回值获得支持；内部等待完成后再返回的同步接口也可能成立，但要确认兼容与并发要求。并未要求另一方案照搬CUTLASS的异步形式。

## 3. 重复调用与参数更新

反例是在 initialize 后只修改原 Arguments，就认为 `run(stream)` 会自动使用新地址。固定源码中参数转换按当时地址和stride构造执行表示，stream重载只读取保存的params_。

同时保留两个容易被反向误判的区别：复用原参数并非错误，只要存储与依赖有效；保存地址不等于深拷贝矩阵内容，在同一地址更新数据不能与更换地址混为一谈。update不初始化workspace，非空也不证明容量；但不能由此反推任何更新都必须完整initialize。

## 回归与剩余义务

主线17项测试和页面39项DOM-double测试通过，新增判定入口保持独立来源引用与条件，不删除原图边。全站产物检查零问题，原atlas.json的字节、606节点、977边、824文件保持不变。

本轮只有Host布局地址计算实际执行；完成与复用案例是固定源码分析，P0/P1是讨论符号，不是实际GPU指针。GPU运行、真实浏览器、同事方案与独立使用者验收仍未完成，原全库目标继续保留。

这三个案例已足够承担当前主线的判定示范，不以增加案例数量继续扩展此检查点。后续应优先核对主线中尚缺证据的关键交接，再按原模块/全库账本推进，避免把展示完善当成源码覆盖进展。
